## A · 可部署性：让它能被别人打开

`TODO.md` 把「公开可访问的在线 Demo」列为 P0，但真正卡住它的不是部署配置，是鉴权。
当前服务只要暴露到公网，任何人都能读走全部项目的接入凭据、改 Issue 状态、
往任意 Release 上传 Source Map。这条主线必须最先做完。

### A1 接入凭据与访问凭据没有分离，且接入凭据会被公开返回（已核实缺陷）

**现状**　`dsnKey` 是全系统唯一凭据，而它只把守了 `POST /api/v1/envelopes` 一条路由。

- `GET /api/v1/projects`（`routes/projects.ts:18`）返回的 `listProjects` 结果中
  **包含每个项目的 `dsnKey`**（`services/queries.ts:82`）。
- `cors({ origin: true })`（`app.ts:48`）回显任意来源，任何网页都能直接读到这份列表。
- `POST /api/v1/releases/:id/source-maps` 无鉴权：可覆盖任意 Release 的 map，
  而还原后的原始源码会出现在 Issue 详情里。
- `PATCH /api/v1/issues/:id/status` 无鉴权。

**改法**　拆成三类凭据：DSN Key 公开、只写、仅接入；会话凭据读查询接口与改 Issue 状态，
按项目授权；上传凭据只能传 Source Map，供 CI 使用。`dsnKey` 移出列表响应，只在会话凭据下的
项目详情接口返回。把「这条路由需要什么凭据」做成显式声明，缺省即拒绝。

**验收**　一条测试遍历 Fastify 路由表，任何未声明鉴权策略的路由直接让测试失败——新增路由
默认安全，而不是默认公开。另有负向测试断言未鉴权请求拿不到 `dsnKey` 字段。

### A2 接入端点和查询端点需要相反的 CORS 策略（已核实现状）

**现状**　两类端点共用一条 `origin: true`。这对接入端点是必需的——遥测来自客户自己的域名，
来源天然不可枚举；但对查询端点是纯粹的敞口。

**改法**　按前缀分成两个 CORS 作用域：`/api/v1/envelopes` 保持开放且只允许 `POST`；
其余路由白名单 Dashboard 源，携带凭据。顺带补上 `helmet` 的基础响应头。

**验收**　集成测试用陌生 `Origin` 分别打两类端点，断言接入通过、查询被拒。

### A3 接入端点没有限流（设计提案）

**现状**　`bodyLimit` 限制了单个请求体，但没有任何按 DSN 或按 IP 的频率约束。
SDK 侧的 `maxQueueSize` 只保护浏览器内存，保护不了服务端。

**改法**　每个 DSN 一个令牌桶，超限返回 `429` 与 `Retry-After`；SDK 侧识别并遵守这个头
（与 B1 同一次改动完成）。配额与当前用量进 `/metrics`（见 D3）。

**验收**　基准脚本增加「超配额」场景，断言服务端返回 429 且未写库，SDK 在 `Retry-After`
之前不再发送。

### A4 部署产物与演示数据的可恢复性（设计提案）

**现状**　只有本地启动路径。`seed.ts` 已经能幂等重建演示项目（先清
`diagnoses / events / issues / releases` 再写入），这正好是定时重置需要的原语。

**改法**　三个应用一份 Dockerfile + compose；SQLite 与 Source Map 目录挂持久卷；
定时任务按小时跑 `pnpm seed`。公开环境不放任何真实密钥——无 `MODEL_API_KEY` 时诊断本就
降级到本地引擎，Demo 因此可以零成本运行。

**验收**　无登录状态的浏览器走通「演练场制造事故 → 工作台看到 Issue → 还原堆栈 → 出诊断」，
并把这条路径加入 `smoke:production`。

## B · 韧性：异常路径上的行为

正常路径已经打磨得很细。但监控系统的价值恰恰在事故当天兑现——那天服务端可能正在返回 5xx、
页面可能正在崩溃刷新、Source Map 可能刚好很大。

### B1 一个被永久拒绝的批次会把整条上报队列堵死（已核实缺陷）

**现状**　`Transport.sendWithRetry` 对**任何**非 2xx 一律重试，重试用尽后 `flush` 把这一批
原样放回队首（`Transport.ts:165` 的 `queue.unshift(...batch)`）。下一次 `flush` 又从队首
取走同一批。

于是只要服务端**确定性地**拒绝这批（Schema 升级后的 `400 INVALID_ENVELOPE`、DSN 轮换后的
`403`），队列就进入死循环：新事件永远排在这批后面，直到撞上 `maxQueueSize` 被逐个丢弃。
这不是「重试几次后失败」，是**队头阻塞导致的全量静默丢失**。

**改法**

- 按响应分类而不是按成败分类：`408 / 429 / 5xx` 与网络错误可重试，其余 `4xx` 不可重试。
- 不可重试的批次**丢弃**并计入 `rejected` 计数，绝不放回队首。
- `429` 遵守 `Retry-After`，与 A3 的服务端限流对齐。
- 把 `dropped()` / `rejected()` 通过公开的 `stats()` 暴露出去——采集缺口本身就是一条证据。

**验收**　负向测试：先让接入端点固定返回 400，再恢复正常，断言随后入队的事件**能**送达
（当前实现会在这一步失败），且被拒批次只计数不重投。

### B2 Source Map 还原挂在接入响应路径上，且 Consumer 缓存只活一次调用（已核实现状）

**现状**　`routes/events.ts:29` 在返回 `202` 之前，对批次里每条带堆栈的事件逐个
`await symbolicateStack`。而 `sourcemaps.ts:109` 的 Consumer 缓存是**函数内的局部
`Map`**——它只避免了「同一条堆栈的多个帧重复解析同一份 map」，跨事件完全不复用。

结果：一批 10 条同 Release 的错误，会把同一份 map 的 VLQ mappings 解析 10 次
（每次还要初始化一次 WASM）。接入延迟因此与 Source Map 的大小成正比，而 `202` 承诺的语义
只是「已接收」。`symbolicateReleaseEvents` 的回填是同样的形状，整个 Release 一遍。

**改法**

- 进程级 LRU 缓存 Consumer，键为 `map_path` + `mtime`，淘汰时显式 `destroy()`——
  代码里已有的「Consumer 持有 WASM 内存」那条注释，正是这个缓存必须显式淘汰的理由。
- 把还原移出响应路径：入库事务提交后返回 `202`，还原交给 after-response 的任务队列。
- 失败与缺失分别计数，让「还原命中率」成为可观测指标而不是猜测。

```
现在：Zod 校验 → 入库事务 → 逐事件还原（重复解析 map） → 202
改后：Zod 校验 → 入库事务 → 202 → 异步还原（LRU 复用 Consumer）
```

**验收**　`benchmark.ts` 增加「N 条堆栈 × 一份 M 帧 Source Map」场景，把改前改后的 P50/P95
按现有表格格式写进 `docs/reports/performance.md`。

### B3 队列只在内存里，页面刷新或崩溃即全部丢失（设计提案）

**现状**　退出路径已经做得很扎实（`pagehide` / `visibilitychange` 触发整队列 `sendBeacon`，
配额不足回落 `keepalive fetch`）。但 beacon 被拒或标签页被系统杀死时，队列随页面一起消失——
而这恰好是白屏类事故最典型的收场方式。

**改法**　可选的 `persistQueue`：以字节上限写入 `localStorage`，下次 `start()` 时回灌并按
`eventId` 去重（服务端幂等已经就位，重复回灌是安全的）。默认关闭，因为它把遥测落在了用户
设备上，这个取舍必须由接入方显式做出。

**验收**　Playwright 用例：入队后直接 `context.close()`，重开页面断言事件补送；
同时 `pnpm measure:sdk` 的体积预算必须显示这个特性的字节代价。

### B4 事件表只增不减，没有保留策略（已核实现状）

**现状**　全仓库唯一的 `DELETE FROM events` 在 `seed.ts` 里，用途是重建演示数据。
每条事件还完整存了一份 `context_json` 与 `breadcrumbs_json`，存储放大明显。

**改法**

- 按项目配置保留窗口，定时删除过期事件；`events_created` 索引已经在了，正好服务这个删除。
- 删除会让 `event_count` 与实际行数产生偏差——明确**选一个**：要么同步扣减，
  要么承认它是「累计发生次数」并写进文档，不要留成含糊。
- 删除后跑 `PRAGMA optimize`，定期 `VACUUM`。

**验收**　测试写入跨窗口的事件，执行保留任务后断言过期行消失、未过期行完好，
且计数口径与文档一致。

## C · 可测优化：下一轮「测量 → 改 → 设预算」

项目已经把这个循环讲清楚三次，方法论是成立的。这里四个目标的共同点是：现在都还没有被称量过。

### C1 Issue 列表每一行都要单独查一次 Sparkline（已核实现状）

**现状**　`services/queries.ts:211` 在拿到分页结果后逐行循环，每行执行一次 6 小时分桶聚合。
`pageSize` 上限是 100，所以一次列表请求最多触发 101 次查询——这与 README 里已经修掉的
「接入路径写入放大」是同一类问题，只是发生在读路径上。

**改法**　改成一次 `WHERE issue_id IN (...)` 的分组聚合，在内存里按 `issue_id` 分派到各行。
空桶补 0 的逻辑保持不变——那是 Sparkline 不错位的前提。

**验收**　基准脚本按 `pageSize` 1 / 25 / 100 分段测列表 P50，断言延迟不再随页大小线性增长，
结果进性能报告。

### C2 概览查询的 COALESCE 让索引整体失效（已核实现状）

**现状**　`getProjectOverview` 靠 `COALESCE(i.project_id, r.project_id) = ?`
（`queries.ts:297 / 300 / 310`）确定事件归属，因为 `events` 表**没有 `project_id` 列**。
条件里带函数就不是 sargable，任何索引都用不上，24 小时窗口的三项聚合
（含 `COUNT(DISTINCT user_id)`）随事件总量线性变慢。

**改法**　在 `events` 上冗余一列 `project_id`——接入时它本来就是已知的，写入不增加查询。
配 `(project_id, created_at)` 索引后，三项聚合都退化成索引区间扫描。这一步同时是
`TODO.md` P2 里 PostgreSQL 迁移的前置：分区键先在 SQLite 阶段确定下来。

**验收**　用 `EXPLAIN QUERY PLAN` 断言改后走索引而非全表扫描，并在 10 万事件规模下记录改前
改后的概览 P50。

### C3 SDK 有体积预算，Dashboard 没有（已核实现状）

**现状**　路由级 `lazy` 和 ECharts 按需注册都已经做了，`manualChunks` 也拆了长缓存 chunk。
但没有任何数字守着它们：某天有人写一句顶层 `import` 把 ECharts 拉回首屏，`pnpm verify`
不会有任何反应。

**改法**　把 `measure-sdk.mjs` 的做法搬到 Dashboard：给首屏 JS 与每个路由 chunk 各设一个
gzip 预算，超出即非零退出，接进 `pnpm verify`。同时断言 `echarts` 不出现在首屏 chunk 里——
和 SDK 断言产物中不得出现 zod 标识符是同一个手法。

**验收**　故意在首屏组件里顶层引入 ECharts，CI 必须失败；恢复后必须通过。

### C4 建表 DDL 与 Drizzle Schema 双写，靠人记住同步（已核实现状）

**现状**　`db/client.ts` 里的 `INITIAL_SCHEMA` 是完整的手写 DDL，`db/schema.ts` 是等价的
Drizzle 定义。代码注释已经承认「两处结构变更必须保持同步」。这条纪律现在没有任何机器在检查，
而 C2 恰好就要改表。

**改法**　改用 drizzle-kit 生成迁移，`client.ts` 只负责按顺序执行迁移文件。再加一条测试：
从迁移建库，反查实际表结构，与 Drizzle 定义比对，不一致即失败。

**验收**　删掉某个索引的迁移后测试必须失败；补回后通过。旧数据库文件能被迁移脚本就地升级，
不需要重建。

## D · 可信度：让每条结论可复现、也可被反驳

项目最值得保住的特点，是「所有对外数字都能由命令重新生成」。有三处地方还没被这条纪律覆盖。

### D1 诊断评测脚本存在，但不在 verify 和 CI 里（已核实现状）

**现状**　`evaluate:diagnosis` 在 `package.json` 里，但 `verify` 只串了 lint / typecheck /
test / build / measure:sdk / smoke。诊断质量因此是一次性测得的数字，没有回归防线——
改一次 Prompt 或换一次模型都不会有人察觉。

**改法**

- 固定一组黄金样本，断言结构化成功率与「每条结论都能回指证据」的比例不低于阈值。
- 同时设 token 预算：单次诊断的输入 token 超过上限即失败，防止上下文裁剪逻辑被无声改坏。
- 无 Key 的环境跑本地引擎分支，让这条门禁在 CI 里零成本执行。

**验收**　CI 里 `evaluate:diagnosis` 与其他门禁同级；报告落盘，README 引用的诊断数字由它生成。

### D2 测试缺口集中在两个最复杂的文件上（已核实现状）

**现状**　全仓 11 个测试文件，质量不低。但 `services/queries.ts`（503 行，全部动态 SQL
拼装与分页）没有任何单元测试，`services/events.ts`（209 行，聚合与计数）只被 `app.test.ts`
间接覆盖。而 C1 / C2 要改的正是这两个文件。

**改法**　按包设覆盖率目标，而不是设一个全仓百分比——后者会诱导为凑数写无意义的测试。
优先补：筛选组合（release / browser / route / search 叠加）、排序白名单、分页边界、空结果，
以及计数在删除与去重下的口径。

**验收**　先补测试再动 C1 / C2：优化前后的行为一致性由这批测试保证，而不是靠人眼比对。

### D3 一个可观测平台，观测不到自己（设计提案）

**现状**　服务端只有 `/health` 返回 `{ status: 'ok' }`。接入速率、Source Map 还原命中率、
诊断降级比例、SDK 侧的丢弃计数——这些数字目前只能靠翻日志。

**改法**

- 暴露 `/metrics`，把上面几项做成计数器；A3 的配额用量和 B1 的 `rejected` 都汇入这里。
- 让 Dashboard 自己接入 TracePilot SDK，上报到同一个服务的独立项目——自用是最诚实的验证：
  SDK 的性能开销和 teardown 正确性会先影响作者自己。

**验收**　Dashboard 的真实错误出现在它自己的 Issue 列表里；演示脚本增加一步
「用 TracePilot 排查 TracePilot」。

## 执行顺序

1. **先把凭据分开**（A1 → A2）。没有 A1，后面所有「部署上去」的动作都会连带把 `dsnKey`
   和 Source Map 上传口暴露出去。
2. **再修会丢数据的那两条路径**（B1 ∥ B2）。两者互不依赖，可以并行；但都要赶在有真实流量
   之前，否则第一批丢的就是真数据。
3. **上线，拿到真实流量**（A3 → A4）。上线之后才有值得测量的负载，也才有 P0 要的那个
   「一个链接跑通 5 分钟」。
4. **补测试，然后动查询层**（D2 → C1 ∥ C2 → C4）。D2 排在前面不是形式主义：这两处优化会
   重写动态 SQL 的拼装和聚合口径，没有行为基线就无法证明「只是变快了，没有变错」。
5. **把新能力也纳入门禁**（D1 ∥ C3 → B3 ∥ B4 ∥ D3）。前两项是给所有改动装的锁，
   后三项价值高但不阻塞任何人。

## 明确不做

- **Session Replay**：录制与回放是另一套完整的工程问题（DOM 快照、增量序列化、隐私遮罩），
  和「证据链 + 可核验诊断」的主线没有交集。
- **Kafka / Kubernetes**：当前是单写者 SQLite 的单机 MVP，引入它们只会得到一套没有负载
  支撑的配置文件。真正该先做的是 C2 的分区键和 B4 的保留策略。
- **自动修复 / 自动提 PR**：与核心约束直接冲突——诊断被刻意限制为只读、只能引用已存储的证据。
- **换掉 SQLite**：迁移到 PostgreSQL / ClickHouse 先写成经过论证的设计方案，不急于实现。
  C2、C4 是这份方案的实际准备工作。
