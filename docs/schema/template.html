整段 DDL 里最值得讲的一个决定

六条外键，四条 CASCADE、两条 SET NULL。判断标准只有一句话。

ON DELETE CASCADE ×4

子记录脱离父记录之后毫无意义，所以一起删干净，不留孤儿。

  • releases → 没有项目的版本号是什么？
  • issues → 不属于任何项目的问题？
  • source_maps → 没有 Release 的 map 映射不回任何东西
  • diagnoses → 诊断的对象都没了，结论还有什么用

ON DELETE SET NULL ×2

子记录自身仍有价值，所以留下来，只把失效的引用置空。

  • events.issue_id → Issue 是我们「归纳」出来的
  • events.release_id → 版本是我们「关联」上去的
  • 但事件本身是浏览器上真实发生过的观测记录
  • 删掉归纳结论，不该抹掉原始观测
判断外键该用哪个策略，问一句就够：这条子记录脱离父记录之后，还有价值吗？ 有 → SET NULL；没有 → CASCADE。 这也解释了 SQL 教程练习数据里那两条 issue_id 为 NULL 的「孤儿事件」—— 它们正是 SET NULL 的产物。

17 个索引，其中只有 6 个是手写的

每个 UNIQUE 约束会让 SQLite 自动生成一个索引（sqlite_autoindex_*）， 所以真正由 CREATE INDEX 建的只有 6 个。索引加速读，但每次写都要多维护一份—— events 是写入最频繁的表，所以只建了真正用得上的 4 个。

来源 表 索引名 列 唯一
复合索引的列顺序有讲究。events_issue_user (issue_id, user_id) 就是 README「技术难点 2」的主角：它让「该用户是否已在此 Issue 出现过」的判定代价 与 Issue 已有事件数无关，user_count 才能做增量累加。 没有它就得扫该 Issue 的全部事件，单次写入退化成 O(n)。

三个跑出来才发现的细节

都在上面那个真实建的库里验证过，不是从文档上抄的。

01 TEXT PRIMARY KEY 居然可以是 NULL

内省结果里六张表的 id 全都显示 nullable。这不是读错了—— SQLite 为兼容一个很早期的版本行为，只有 INTEGER PRIMARY KEY 才隐含 NOT NULL，其它类型的主键不强制。实测： 

INSERT INTO projects (id,name,dsn_key,created_at) VALUES (NULL,'x','k1',1);
⚠️ 插进去了  → [{"id":null,"name":"x"}]
再插一条 NULL 也可以 → 2 行

-- 对比 INTEGER PRIMARY KEY：NULL 会被自动分配 rowid
INSERT INTO t_int (id,v) VALUES (NULL,'auto');  → [{"id":1,"v":"auto"}]

实际上不会出事，因为 id 全部由 randomUUID() 在应用层生成、 Drizzle 也一定会带上这一列。但严格写法应该是 id TEXT PRIMARY KEY NOT NULL。

02 event_count 的 DEFAULT 1 是个永不生效的遗留

DDL 写的是 event_count INTEGER NOT NULL DEFAULT 1，但全项目唯一插入 issues 的地方（services/events.ts:95）显式写死了 eventCount: 0，注释还专门解释过为什么必须从 0 起步： 「避免新建 Issue 的首条事件被同时计入初始值和增量而重复计数」。

所以这个 DEFAULT 1 是性能优化之前的残留——老实现里新建 Issue 时首条事件就算 1，改成增量累加后起点变成 0，DDL 没跟着改。目前无害， 但哪天有人写个裸 INSERT 忘了带这一列，会静默得到 1，和增量设计差 1。

03 schema.ts 里那些具名唯一索引，数据库里并不存在

db/schema.ts 声明了 uniqueIndex('issues_project_fingerprint')， 但内省结果里根本没有这个名字，只有 sqlite_autoindex_issues_2。

原因就是 client.ts 注释说的那件事：真正建表的是 DDL， schema.ts 只是给 TypeScript 看的类型声明。DDL 写的是表级 UNIQUE(...)（SQLite 自动命名），schema.ts 声明的是具名唯一索引—— 约束效果相同，索引名不同。

不影响正确性，但正好印证了那句警告：「两处结构变更必须保持同步」。 这是用 MVP 幂等 DDL 换来的已知成本，注释里也写了正式演进应替换为版本化 migration。
