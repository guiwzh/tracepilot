章节

    TracePilot · 给前端的服务端入门

    从 fetch 到 server

    你已经写过成千上万次 fetch 了。服务端做的是同一件事的另一端：你发出去的那个请求， 在对面被拆成方法、路径、查询参数和一个字节流，再被组装成一个响应发回来。这份教程按对照译文的方式写： 左边是你熟悉的浏览器端，右边是服务端收到它时的样子。

    所有代码都只用 Node 内置的 node:http——零依赖、零启动 flag。 先用最朴素的方式把一个 server 写出来，最后再看 Fastify 到底替你做了什么。 那时候框架就不再是需要「学」的东西，而是你已经手写过一遍的东西的简写。

    00

    先把练习环境跑起来

    不要只读。服务端和 SQL 一样是手上功夫，而且它比 SQL 更需要动手—— 很多概念（流、状态码、预检）读起来都平平无奇，真正卡住你的是第一次自己写的时候。

    这套练习不用装任何东西，node:http 是 Node 内置的。在仓库根目录执行：

    终端
    # 1. 看有哪些题
node docs/server-tutorial/serve.mjs --list

# 2. 看某一题的题面
node docs/server-tutorial/serve.mjs 01 --prompt

# 3. 答案写进 answers/01.mjs，然后判分
node docs/server-tutorial/check.mjs 01

# 4. 卡住时把答案跑成真 server，手动 curl
node docs/server-tutorial/serve.mjs 01

    第 4 条会把判分用的 curl 命令直接打印出来，复制粘贴就能跑。 写不出来的时候，先把响应打出来看看，比盯着代码猜快得多。

    判分看行为，不看写法

    check.mjs 会真的启动一个 HTTP server 跑你的 handler，发真实请求，比对响应。 所以用正则还是 split、用 writeHead 还是 setHeader、 用 req.on('data') 还是 for await，只要行为一致就算通过。

    答案写在 docs/server-tutorial/answers/，已被 .gitignore 忽略，随便写。

    这跟上一份 SQL 教程什么关系

    数据身份完全一致——一样的 demo-project、iss-hydrate、evt-0001， 一样留了「没有 Issue 的项目」和「没有事件的 Issue」那几个坑。两套练习讲的是同一个系统： 那边练数据怎么查出来，这里练数据怎么经过 HTTP 安全地收进来、发出去。

    区别是这里的数据层是内存对象而不是数据库，因为这份教程的目标是 HTTP，不是再练一遍 SQL。 但 lib/store.mjs 里每个方法都标注了它对应的真实 SQL——换成数据库之后， HTTP 这一层一行都不用改。这就是分层的意义。

    01

    心智模型：进程一直活着

    这是前端转服务端最需要翻转的一个认知。浏览器里，一次刷新什么都没了； 服务端是一个长期活着的进程，模块顶层的代码只在启动时跑一次，之后处理成千上万个请求。

    浏览器：每次刷新都重来
    // 刷新页面 → 这行重新执行
const cache = new Map();

// 用户关掉标签页 → 全没了
    服务端：启动时跑一次，然后一直在
    // 进程启动时执行一次
const db = createDatabase(path);

// 之后所有请求共用这一个 db
// 进程不死，它就不死

    TracePilot 里就是这样：apps/server/src/app.ts 的 createDatabase() 整个进程只调用一次，那个数据库连接被之后所有请求共享。 模块顶层代码 = 启动代码，这个等式记住了，很多写法就都说得通了。

    由此带来的三个后果

    1. 内存泄漏是真问题。浏览器里你不小心留个全局变量，用户刷新就清了。 服务端的进程要活几天几周，每个请求漏一点，最后就是 OOM。

    2. 全局可变状态会跨请求串味。模块顶层写 let currentUser，两个请求并发过来就会互相覆盖。 请求相关的状态必须留在 handler 内部。

    3. 一个没抓的异常可能弄死整个进程。浏览器里报个错顶多这个页面坏了； 服务端的未捕获异常会让 Node 退出，所有用户一起断。 这就是 app.ts 末尾 setErrorHandler 存在的理由。

    顺带一提，apps/server/src/index.ts 用的是 process.exitCode = 1 而不是 process.exit(1)。区别是前者「标记退出码，等事情做完再退」， 后者「立刻退，日志可能还没冲刷到磁盘就没了」。注释里写了这一点。

    02

    一个请求的两端

    你写的每个 fetch，在服务端都会变成一个 req 对象。 把这两边并排看一次，服务端就不神秘了：

    你写的（浏览器端）
    fetch(
  '/api/v1/issues/iss-hydrate?limit=50',
  {
    method: 'PATCH',
    headers: {
      'Content-Type': 'application/json',
    },
    body: JSON.stringify({
      status: 'resolved',
    }),
  },
);
    服务端收到的（req 对象）
    req.method
// → 'PATCH'

req.url
// → '/api/v1/issues/iss-hydrate?limit=50'
//   注意：没有协议，没有域名

req.headers['content-type']
// → 'application/json'  （键一律小写）

// body 呢？不在属性里。
// req 本身就是个流，要自己读。见第 05 章。

    三个立刻要记住的点：

    • req.url 不是完整 URL。它只有路径和查询串。 想用 URL 类解析，必须补一个 base： new URL(req.url, 'http://localhost')。
    • 请求头的键一律是小写。你在浏览器里写 'Content-Type'，服务端读到的是 req.headers['content-type']。 HTTP 头名本来就不区分大小写，Node 统一转小写了。
    • body 不是属性。这是最大的差异，单独用一章讲。
    路径参数和查询参数的分工

    /api/v1/issues/iss-hydrate?limit=50 里， iss-hydrate 是路径参数（定位「哪个资源」）， limit=50 是查询参数（修饰「怎么返回」）。

    这个分工不是硬规定，但是行业惯例，也是 TracePilot 遵守的： /api/v1/issues/:issueId 用路径定位 Issue， ?page&pageSize&status&level 用查询控制筛选和分页。 面试时被问「什么时候用 path 什么时候用 query」，答这个就对了。

    03

    res：状态码、头和 body 都要你自己写

    浏览器端 fetch 帮你把响应解析成了 Response 对象， .json() 一调用就拿到数据。服务端这一侧什么都没有，全要自己组装。

    你习惯的读取方式
    const res = await fetch(url);

res.status       // 200
res.headers.get('content-type')
const data = await res.json();
// ↑ 自动解析
    服务端的写入方式
    res.writeHead(200, {
  'Content-Type': 'application/json; charset=utf-8',
});
res.end(JSON.stringify(data));
// ↑ 要自己 stringify，Node 不替你猜

    整个服务端编程，很大一部分就是在决定这三件事：状态码是多少、带哪些头、body 是什么。 所以练习 01 就是纯粹的这个。

    res.end() 只能调用一次

    响应一旦发出去就结束了。第二次调用 res.end() 或 writeHead() 会抛 ERR_STREAM_WRITE_AFTER_END / ERR_HTTP_HEADERS_SENT。

    新手最常见的写法错误是忘了 return：

    if (!issue) {
  json(404, { error: 'ISSUE_NOT_FOUND' });   // 忘了 return
}
json(200, issue);   // 💥 又发一次，进程报错

    所以本教程的参考答案里，每个分支都写成 return json(...) 或者 json(...); return;。 Fastify 里这个问题轻一些——handler 的返回值就是响应体，不需要手动 end。

    另外注意 Content-Type 必须自己设。不设的话 Node 不会加这个头， 浏览器就得靠猜，fetch().json() 可能直接失败。 练习 01 会检查这个头。

    04

    路由：URL 要自己拆

    没有框架的时候，「路由」就是一串 if。这件事做一遍，你就知道 Fastify 的 app.get('/api/v1/issues/:issueId', ...) 到底省了什么。

    手写（练习 04 要你做的）
    const url = new URL(req.url, 'http://localhost');
const seg = url.pathname.split('/');
// '/api/v1/issues/iss-hydrate'
// → ['', 'api', 'v1', 'issues', 'iss-hydrate']
//    ↑ 注意开头的空字符串

if (seg.length === 5 && seg[3] === 'issues') {
  const issueId = seg[4];
  // ...
}
    Fastify（项目里真实的写法）
    app.get(
  '/api/v1/issues/:issueId',
  async (request, reply) => {
    const issueId = request.params.issueId;
    // ...
  },
);

    框架做的是「把 URL 模式编译成一棵树，然后一次匹配出方法 + 路径 + 参数」。 Fastify 用的是 radix tree，这也是它比 Express 快的主要原因之一。 但概念上就是上面左边那段，只是更快更整齐。

    查询参数拿到的永远是字符串

    url.searchParams.get('page') 返回 string | null， 永远不会是数字。所以 TracePilot 的 routes/issues.ts 里有个 positiveInteger() 专门做转换和夹紧—— 这是练习 08 的内容，也是信任边界的第一课。

    05

    body 是一个流，不是属性

    这是整份教程里最重要的一章。前端所有人都在这里卡过一次。

    fetch 帮你把 body 封装成了 await res.json()， 一行就拿到。服务端没有这一层：请求体是分块到达的， req 本身就是一个可读流，你要自己把块拼起来。

    你以为的
    // ❌ 这个属性不存在
const body = req.body;

// undefined
    实际要写的
    function readBody(req) {
  return new Promise((resolve, reject) => {
    const chunks = [];
    req.on('data', (c) => chunks.push(c));
    req.on('end', () => {
      const raw = Buffer.concat(chunks);
      resolve(raw.toString('utf8'));
    });
    req.on('error', reject);
  });
}

const raw = await readBody(req);
const body = JSON.parse(raw);

    Node 18+ 里 req 也是异步可迭代的，所以还有个更短的写法， 两种都行（练习判分不关心你用哪种）：

    更短的等价写法
    let raw = '';
for await (const chunk of req) raw += chunk;
    为什么要设计成流

    因为 body 可能很大。如果 Node 强行把每个请求体都读进内存再给你， 一个 2GB 的上传就能把进程打死。流让你可以边收边处理， 或者在发现太大时提前掐断。

    TracePilot 就用了后者：app.ts 里 bodyLimit: 1_048_576（1MB）， 注释写得很明白——「在框架解析 JSON 前限制请求体，防止超大遥测包耗尽内存」。 Source Map 上传那条路径是单独的 10MB 上限，因为 .map 文件本来就大。

    这是一道面试题的标准答案：「为什么 Node 的请求体是流？」 —— 因为内存是有限的，而请求体大小是客户端说了算的。

    还要注意：JSON.parse 遇到坏数据会抛异常。 网络来的 body 一定会有坏数据（爬虫、探测、写错的客户端）， 所以必须 try/catch，返回 400，而不是让进程崩掉。练习 05 会测这个。

    06

    状态码：用对了它就是文档

    前端对状态码的印象通常是「200 好、404 没了、500 后端炸了」。 写服务端要精确得多——状态码是 API 契约的一部分， 客户端靠它决定要不要重试、要不要提示用户、要不要跳登录。

    这是 TracePilot 实际用到的全部状态码，每个都有明确分工：

    项目里的状态码分工8 个
    码 含义 项目里用在哪
    200 成功，body 是结果 所有 GET 查询、PATCH 改状态
    201 成功，并且创建了新资源 Source Map 上传成功
    202 已接收，但不保证处理完了 遥测接入 /api/v1/envelopes
    400 你发的东西格式不对 Zod 校验失败、状态值非法
    403 格式对，但你没权限 DSN Key 无效、projectId 对不上
    404 这个资源不存在 Issue / Release 查不到
    415 格式对，但类型我不收 上传的不是 .map 文件
    500 我这边炸了，不是你的错 setErrorHandler 兜底
    202 是个值得讲的选择

    遥测接入返回的是 202 Accepted 而不是 200。 差别在语义：200 说「做完了」，202 说「收到了，后面的事你不用等」。

    routes/events.ts 的注释写了原因—— 「表示服务端已经接收并处理该遥测批次，不要求浏览器等待后续调查动作」。 监控 SDK 发完就该走人，不该为了等服务端做完聚合而拖慢宿主页面。 用 202 就是在协议层面把这件事说清楚。

    400 和 404 的顺序会暴露你的水平

    PATCH /api/v1/issues/不存在的 id/status，body 里的 status 也是非法值。 该返回 400 还是 404？

    400。先校验输入格式，再查资源存不存在。 理由：格式都不对的请求，服务端根本没必要去查数据库； 而且「你的参数写错了」比「这个东西不存在」对调用方更有用—— 后者会让人以为是数据问题，白白排查半天。

    练习 06 专门测了这个顺序，有一条用例就是「不存在的 Issue + 非法 status」。

    07

    CORS：那个报错其实是服务端的事

    每个前端都见过这句： Access to fetch at ... has been blocked by CORS policy。 很多人以为是浏览器在找茬，或者以为是自己 fetch 写错了。都不是。

    CORS 是一组响应头，由服务端发出。 浏览器只是执行者：它看服务端有没有在响应里说「我允许这个来源读我」， 没说就拦下来，不给 JS 读。请求其实已经发出去了—— 这一点很多人不知道，所以「CORS 报错了但数据库里已经写进去了」是完全可能的。

    你看到的（浏览器端）
    // Dashboard 跑在 :4173
// Server  跑在 :4318
// 端口不同 = 跨源

fetch('http://localhost:4318/api/v1/projects')
// ❌ blocked by CORS policy
    要在服务端加的（练习 07）
    res.setHeader(
  'Access-Control-Allow-Origin',
  '*',
);

// 预检请求直接放行，不走业务逻辑
if (req.method === 'OPTIONS') {
  res.writeHead(204, {
    'Access-Control-Allow-Methods':
      'GET, POST, PATCH, OPTIONS',
    'Access-Control-Allow-Headers': 'content-type',
  });
  return res.end();   // 204 = 无 body
}

    TracePilot 里这件事由 @fastify/cors 插件做，就在 app.ts 那一行 app.register(cors, { origin: true, ... })。 手写一遍之后你就知道那个插件在干什么了。

    预检（preflight）是什么

    「简单请求」（GET、或者 Content-Type 是表单类型的 POST）浏览器直接发。 但只要你带了 Content-Type: application/json、 自定义头、或者用了 PATCH/DELETE，浏览器会先发一个 OPTIONS 请求问一句， 服务端答应了才发真正的请求。

    这就是为什么你的接口明明是 POST，DevTools 里却看到两条记录。 也是为什么 OPTIONS 必须在业务逻辑之前处理掉—— 它不该走进你的路由匹配，更不该因为「没有这个方法」被 405 拒绝。

    origin: '*' 在开发和公开只读 API 上没问题。 但一旦要带 Cookie 凭证，* 就不允许了，必须回显具体来源并加 Access-Control-Allow-Credentials。TracePilot 是单用户 MVP，没走到这一步。

    08

    信任边界：网络来的东西一律不可信

    从这一章开始，讲的不再是「怎么让它跑起来」，而是「怎么让它不出事」。 这部分是服务端和前端心态差别最大的地方，也是面试最容易问出深度的地方。

    一句话原则：凡是从网络进来的，都当成攻击者精心构造的。 不是因为悲观，而是因为成本不对称——你多写三行校验，对方要绕过就得多花几个数量级的力气。

    前端的假设
    // 这个值来自我自己写的表单
// 我知道它是 1~100 的整数
const pageSize = form.pageSize;

fetch(`/api/issues?pageSize=` + pageSize);
    服务端必须的假设
    // 这个值可能是：
//   -1       → 非法 LIMIT
//   999999   → 一次拖垮数据库
//   'abc'    → NaN
//   3.7      → 小数
//   (不传)   → undefined
const pageSize = positiveInteger(
  query.pageSize, 25, 100,
);

    positiveInteger 是 TracePilot 真实存在的函数，就在 routes/issues.ts 开头。它只有五行，但这五行挡住的是 「有人把 pageSize 改成 9999999 然后你的服务器开始往内存里塞一百万行」。

    apps/server/src/routes/issues.ts
    function positiveInteger(value, fallback, maximum) {
  // 查询参数均来自字符串；夹紧范围可避免负 LIMIT 或一次读取过多事件。
  const parsed = Number(value ?? fallback);
  if (!Number.isFinite(parsed)) return fallback;
  return Math.max(1, Math.min(maximum, Math.floor(parsed)));
}
    Number() 的三种空值行为要分清

    Number('') 是 0， Number(null) 是 0， Number('abc') 是 NaN， Number(undefined) 也是 NaN。

    所以不能只写 Number(x) || fallback——那样 pageSize=0 和 pageSize=abc 会走同一条路， 而且真正传 0 的时候你分不清是「用户传了 0」还是「没传」。 先判 Number.isFinite，再夹紧，才是对的。练习 08 把这几种输入都测了。

    还有一个更重要的信任边界：SQL 注入。 queries.ts 里有一段动态拼 WHERE 的逻辑，注释特意写明了纪律： 「SQL 片段来自固定代码，所有用户值都进入 params 占位符」。

    ❌ 绝对不能这么写
    db.prepare(
  `SELECT * FROM issues
   WHERE status = '` + query.status + `'`
).all();

// status = "' OR '1'='1"
// → 整张表被读走
    ✅ 项目里的写法
    conditions.push('i.status = ?');
params.push(query.status);

// SQL 文本里只有 ?，用户值单独传
// 数据库不会把它当语法解析
db.prepare(sql).all(...params);
    09

    运行时校验：TypeScript 在这里帮不了你

    这是前端最容易误判的一点。项目是 TypeScript 写的，接口也声明了类型， 很自然会觉得「类型系统会帮我挡住脏数据」。

    不会。TypeScript 的类型在编译后全部消失。

    看起来安全（其实是谎言）
    interface Envelope {
  dsnKey: string;
  events: MonitorEvent[];
}

app.post('/api/v1/envelopes', (req) => {
  const body = req.body as Envelope;
  // ↑ as 只是让编译器闭嘴
  //   运行时 body 可能是 null、字符串、
  //   或者 events 是个数字
  body.events.length;  // 💥
});
    项目里真实的写法
    const parsed = envelopeSchema.safeParse(req.body);
if (!parsed.success) {
  return reply.code(400).send({
    error: 'INVALID_ENVELOPE',
    details: parsed.error.flatten(),
  });
}
// 到这里 parsed.data 才真的是 Envelope
const result =
  ingestEnvelope(db, parsed.data);

    这就是 Zod 存在的全部理由：它在运行时检查一个 unknown，检查通过后再用 z.infer 把静态类型推导出来。 一份 schema 同时管住编译期和运行期，两边不会漂移。

    为什么 schema 放在 shared 包里

    packages/shared/src/schemas.ts 被 SDK、Server 和 Dashboard 同时依赖。 SDK 按它构造事件，Server 按它校验，Dashboard 按它推导 DTO 类型。

    好处是字段改一处，三端一起报错。 如果三边各写各的类型，SDK 改了个字段名，Server 只会在运行时静默收到 undefined，然后你在生产环境查两天。

    练习 09 让你手写一个迷你版：检查 dsnKey 是非空字符串、 events 是非空数组、每个 event 有必需字段， 并且一次返回全部错误而不是遇到第一个就停。 写完你就明白 error.flatten() 是在解决什么问题了。

    10

    脱敏：数据离开浏览器之后

    监控 SDK 会把错误、请求、用户行为发到服务端存起来。 这意味着用户页面上的任何东西都可能被顺手带走—— 请求头里的 Authorization、URL 里的 ?token=、 表单里的密码字段。

    这不是假想。真实的监控系统出过很多次这种事故： 错误消息里带着完整的 JWT，然后整个团队都能在 Dashboard 上看到。

    packages/shared/src/redaction.ts

  /authorization|cookie|password|passwd|secret|token|api[-_]?key/i;

function redactSensitive(value, depth = 0) {
  // 限制递归深度既避免恶意超深对象，也防止遥测清理本身拖慢宿主页面。
  if (depth > 8) return '[Max depth]';

    为什么服务端还要再脱敏一次

    SDK 里已经有 beforeSend 钩子让业务方清理了， 服务端入库前还会再调一次 redactSensitive。 看起来重复，其实是必须的。

    理由写在 services/events.ts 的注释里： 「即使 SDK 已运行 beforeSend，Server 仍把客户端数据视为不可信并二次脱敏」。 SDK 跑在用户的浏览器里——那是攻击者完全控制的地方。 他可以改掉你的 SDK，可以直接 curl 你的接入接口。 客户端的任何清理都只是「优化」，不是「保证」。

    事实上还有第三道：调用外部模型之前又脱敏了一次 （diagnosis.ts 的 buildDiagnosisContext）， 注释说这是「防止历史脏数据进入外部模型」。 三道防线，每一道都假设前一道可能失效。

    app.test.ts 里有一条断言专门锁这件事： 造一个带 authorization: 'Bearer should-never-be-stored' 的事件， 入库后查详情，断言响应里不含那个字符串、且含 [REDACTED]。练习 10 就是这个逻辑的简化版。

    11

    幂等：网络一定会重试

    手机从电梯里出来、Wi-Fi 切 4G、服务端超时—— 监控 SDK 会重发同一批事件。如果服务端老老实实每次都写进去， 一个错误会被统计成十次，Dashboard 上的数字就全是假的。

    解法叫幂等：同一个操作做一次和做十次，结果一样。 做法是让客户端给每条事件生成一个唯一 eventId，服务端按它去重。

    apps/server/src/services/events.ts
    const duplicate = db.prepare('SELECT 1 FROM events WHERE id = ?')
  .get(rawEvent.eventId);
if (duplicate) {
  // eventId 是幂等键，浏览器重试同一批次不会重复写入。
  duplicates += 1;
  continue;
}
    幂等键换来的性能优化

    这里有个值得讲的连锁反应。既然重复批次在插入前就被拦掉了， 那么 Issue 的 event_count 就不需要每次重新 COUNT(*)， 直接 +1 就是对的。

    TracePilot 早期版本为了保证幂等，每条事件入库都用 COUNT(*) 从 events 表重新派生计数—— 单次写入因此退化为 O(Issue 内事件数)。改成增量之后：

    Issue 内已有事件 改动前 P50 改动后 P50
    1,000 1.79 ms 1.14 ms
    5,000 6.57 ms 0.96 ms
    10,000 12.88 ms 0.98 ms

    从线性增长变成恒定。幂等不只是正确性，它还买来了性能。 这个故事可以直接当面试素材——数字由 pnpm benchmark 复现。

    框架的职责6 项
    你手写时要做的 Fastify 的做法
    拆 URL、比对每一段 '/api/v1/issues/:issueId/status' → request.params

    就这些。Fastify 没有引入任何你不理解的新概念， 它只是把你刚才手写的六件事做得更快、更整齐。 这也是为什么我在开头说「框架不值得当成学习目标」—— 真正的门槛是 HTTP 本身，不是某个框架的 API。

    Fastify 里另外三个要认识的东西

    app.register(插件, 选项) —— 装插件。 @fastify/cors 装的就是你练习 07 手写的那套头， @fastify/multipart 负责文件上传的解析。 注意 app.ts 里是 await app.register(...)—— 注释解释了为什么：「Fastify 插件必须 await 注册完成后再挂载依赖它们的路由」。

    app.addHook('onClose', ...) —— 生命周期钩子。 项目用它在应用关闭时释放 SQLite 文件句柄。测试、热重载、正常退出都会走到。

    app.inject(...) —— 这个最值得学。 它能不监听端口就跑完整个路由栈，所以测试不用抢端口、不用等启动。 app.test.ts 全部用它写的，317 行覆盖了接入、聚合、脱敏、幂等、分页。

    还有一个设计值得单独说：app.ts 导出的是 buildApp() 工厂函数，而不是一个现成的 app 实例。 index.ts 拿到它才 listen。 这样测试可以用临时数据库构造一个独立的 app，基准脚本也能用完全相同的路由栈跑压测—— 「构造」和「启动」分开，是服务端一个很通用的模式。

    为什么这里的数据库调用没有 await

    读 TracePilot 的 server 代码时，你一定会在这里卡一下：

    apps/server/src/routes/issues.ts
    app.get('/api/v1/issues/:issueId', async (request, reply) => {
  const issue = getIssue(database, stringParam(request.params, 'issueId'));
  //    ↑ handler 是 async，但这里一个 await 都没有
  if (!issue) return reply.code(404).send({ ... });
  return issue;
});

    前端的直觉是「所有 I/O 都是 Promise」，所以这看起来像 bug。它不是。

    better-sqlite3 是故意做成同步的。 因为 SQLite 不是那种要走网络的数据库，它就是一个本地文件， 读它和读一个文件没区别。既然没有网络往返，异步带来的调度开销反而比同步读还大。

    你习惯的（PostgreSQL / MySQL）
    // 数据库在另一台机器上
// 要走 TCP，等几毫秒到几十毫秒
const rows = await pool.query(
  'SELECT * FROM issues WHERE id = $1',
  [id],
);
    better-sqlite3（本地文件）
    // 数据库就是本进程能直接读的一个文件
// 微秒级，异步化反而更慢
const row = db
  .prepare('SELECT * FROM issues WHERE id = ?')
  .get(id);
    同步还换来了一个关键能力：事务

    services/events.ts 里整批事件的写入是这样的：

    // better-sqlite3 transaction 接受同步回调，回调抛错时会自动 ROLLBACK。
const ingest = db.sqlite.transaction(() => {
  for (const rawEvent of envelope.events) {
    // 鉴权、幂等、脱敏、聚合、落库……
  }
});
ingest();

    因为回调是同步的，中途不会有别的代码插进来， 所以「要么整批成功，要么整批回滚」是有保证的。 如果这里面混进 await，事务期间控制权会交还给事件循环， 另一个请求就可能在事务中间插一脚——那是非常难查的 bug。

    那怎么区分「真异步」和「假异步」

    同一个文件里，这一行是真的要 await：

    const originalStack =
  await symbolicateStack(database, release.id, stack);

    因为 source-map 库要读磁盘上的 .map 文件并解析， 那是真正的异步 I/O。

    判断方法：看它碰的是什么。 碰 SQLite → 同步；碰文件系统的 fs/promises、网络请求、外部模型 API → 异步。 能一眼分清这两者，你就真读懂这一层了。

    代价当然有，注释里也写明了：SQLite 是单写者模型， 同一时刻只能有一个写事务。项目开了 WAL（journal_mode = WAL） 让读和写更好地并行，又设了 busy_timeout = 5000 避免短暂写锁立刻报错。但这仍然不是能水平扩展的生产数据库—— README 里没有把本地基准包装成生产 SLA，这点很诚实。

    Drizzle：这个项目里只有 6 处

    最后说 Drizzle，因为它在这个项目里的分量比名字听起来小得多。 实际数一下调用点：

    数据访问方式统计（不含测试）53 处
    方式 调用点 用在哪
    原生 SQL prepare() 47 处 几乎所有读查询，以及部分写入
    Drizzle insert / update 6 处 只在 services/events.ts 等写入路径
    Drizzle select 0 处 一次都没用

    所有复杂查询——分页、EXISTS 子查询、json_extract、 时间桶聚合——全是手写 SQL。也就是说，你上一份教程学的 SQL 已经覆盖了数据层九成的代码。

    Drizzle 对你只剩两个知识点：

    • 它不是数据库，是个带 TypeScript 类型的 SQL 生成器。 db/schema.ts 那 111 行声明的是列名和类型， 让 insert().values({...}) 能在编译期查出字段写错。
    • 它和建表 DDL 是两处，必须手动保持同步。 db/client.ts 里的 CREATE TABLE 才真正建表， db/schema.ts 只是给 TypeScript 看的。 注释里明确写了这是 MVP 的取舍：「正式演进时应替换为版本化 migration」。
    这个取舍本身就是面试素材

    被问「为什么写入用 Drizzle，查询用原生 SQL」，答案是清楚的： 写入需要类型安全（字段多、容易写错、改 schema 时要能编译期发现）， 复杂查询需要控制力（ORM 生成的 SQL 很难精确控制分页、子查询和索引使用）。

    两种访问面同时保留，各用在擅长的地方——db/client.ts 的注释就是这么写的：「Drizzle 用于类型安全写入，原生 prepared SQL 用于复杂聚合查询」。

    三个可以带进面试的问题

    「为什么服务端要再脱敏一次？」 因为 SDK 跑在用户浏览器里，那是攻击者能改的地方。客户端清理是优化，不是保证。

    「为什么数据库调用没有 await？」 SQLite 是本地文件，没有网络往返；同步还让事务回调中间不会被其它请求插入。

    「幂等和性能有什么关系？」 有了 eventId 去重，计数就不必每次重新 COUNT(*)，单次写入从 O(n) 变成 O(1)， 一万条事件时 P50 从 12.88 ms 降到 0.98 ms。

    最后一句：这份教程从头到尾没让你装一个依赖。 服务端不是一堆需要背的框架 API，它就是 「把一个字节流拆开，决定要不要信它，然后组装一个响应发回去」。 剩下的都是这件事的变奏。
