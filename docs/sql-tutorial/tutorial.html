    TracePilot · 给前端的数据库入门

    从数组到 SQL

    你已经会用 filter、map、reduce 处理数组了。SQL 做的是同一件事，只是换了一种语法，并且跑在数据旁边而不是内存里。这份教程按对照译文的方式写：左边是你熟悉的 JS，右边是等价的 SQL。

    所有示例都在一个真实的 SQLite 库上跑过，输出是实际执行结果，不是手写的示意。这个库的表结构与 apps/server/src/db/client.ts 完全一致，所以练熟的查询可以直接搬进项目。

    00

    先把练习环境跑起来

    不要只读。SQL 是手上功夫，看懂和写得出之间隔着一段距离，唯一的过法是自己敲。

    好消息是不用装任何东西——Node 22 内置了 SQLite，所以三条命令就够了。在仓库根目录执行：

    终端

node --experimental-sqlite docs/sql-tutorial/seed.mjs

# 2. 随便查点什么
node --experimental-sqlite docs/sql-tutorial/q.mjs "SELECT * FROM projects"

# 3. 做完练习后自测
node --experimental-sqlite docs/sql-tutorial/check.mjs

    命令太长的话，先设个别名，后面就只用敲 q "SELECT ..."：

    终端
    alias q='node --experimental-sqlite docs/sql-tutorial/q.mjs'
    这个库跟你的项目是什么关系

    表结构逐字复制自 apps/server/src/db/client.ts：一样的 projects / releases / issues / events / diagnoses，一样的外键和索引。数据是虚构的，但形状是真的——你在这里写出来的查询，换个库名就能用在 TracePilot 上。

    它写在 docs/sql-tutorial/.data/，与项目自己的 .tracepilot/ 数据库完全隔离，怎么折腾都不会弄坏你的开发数据。删库重来：把 seed 命令再跑一遍。

    01

    心智模型：表就是一个数组

    把数据库想成一个 { [表名]: 对象数组 } 的全局对象，一切就都对上了：

    你已经会的 JS
    const projects = [
  { id: 'demo-project', name: 'Checkout Web' },
  { id: 'mobile-web',   name: 'Mobile Storefront' },
];
    数据库里的对应物
    -- 表 = 数组
-- 行 = 数组里的一个对象
-- 列 = 对象的一个字段
SELECT * FROM projects;

    三条关键差异，记住这三条就不会拧巴：

    • 列是固定的。JS 数组里每个对象可以字段各不相同，表不行——所有行必须有完全相同的列。这是 CREATE TABLE 的作用，相当于给数组加了一个强制执行的 TS 类型。
    • 行是无序的。数组有下标，表没有。没写 ORDER BY 时返回顺序是数据库说了算的，今天这样明天可能那样。任何时候依赖「默认顺序」都是 bug。
    • SQL 是声明式的。你描述要什么，不写怎么拿。中间有个查询优化器决定实际怎么执行——这也是为什么同一句 SQL，加个索引就能快几千倍。
    02

    SELECT：挑哪些列

    SELECT 对应 map：决定每行留下哪些字段。

    JS
    projects.map(p => ({
  id: p.id,
  name: p.name,
}))
    SQL
    SELECT id, name
FROM projects;
    实际输出3 行
    id name
    demo-project Checkout Web
    mobile-web Mobile Storefront
    legacy-admin Legacy Admin

    取全部列、改列名、算新列

    SQL
    SELECT *              -- 所有列，等价于不写 map
SELECT name AS 项目名  -- AS 改列名，等价于 map 里换 key
SELECT event_count / 2 -- 可以直接算，等价于 map 里做运算
SELECT DISTINCT level  -- 去重，等价于 [...new Set(...)]
    写业务代码别用 SELECT *

    调试时随便用，写进代码里就是隐患：以后有人给表加一列，这句查询会悄悄多传一列数据；列的顺序变了，按位置取值的代码会错位。把要的列写全，跟你不会写 ...props 然后祈祷是一个道理。

    03

    WHERE：留哪些行

    WHERE 对应 filter。注意它在 SELECT 后面写，但先执行——先筛行，再取列。

    JS
    issues
  .filter(i => i.status === 'unresolved')
  .map(i => ({ title: i.title,
               level: i.level }))
    SQL
    SELECT title, level
FROM issues
WHERE status = 'unresolved';
    实际输出5 行
    title level
    CheckoutStateError: Checkout state failed to hydrate error
    PromotionError: Promotion response contained an invalid discount error
    CurrencyError: Currency formatter received a non-numeric total warning
    TaxError: Tax estimate request exceeded its deadline error
    ScrollError: Virtual list scroll anchor was lost warning

    条件写法对照

    JS
    a === b          a !== b
a > b            a >= b
a && b           a || b           !a
['x','y'].includes(a)
a >= 5 && a <= 20
s.includes('Error')
s.startsWith('Tax')
    SQL
    a = b            a <> b   -- 或 !=
a > b            a >= b
a AND b          a OR b          NOT a
a IN ('x', 'y')
a BETWEEN 5 AND 20    -- 含两端
s LIKE '%Error%'       -- % 匹配任意长度
s LIKE 'Tax%'         -- _ 匹配单个字符
    三个新手必踩的点

    相等是一个等号。= 就是比较，SQL 里没有赋值语句跟它抢，也没有 == 或 ===。

    字符串只能用单引号。'demo' 是字符串，"demo" 是列名。写错了 SQLite 会报 no such column: "iss-tax"——看到这个报错，先检查引号。

    字符串里的单引号要写两遍。'it''s'，不是反斜杠转义。不过实际写代码时你应该用 ? 占位符，根本不需要自己拼字符串。

    04

    NULL：SQL 里最容易出错的地方

    这一章单独拎出来，因为它是前端转后端翻车率最高的一个点，而且错了不报错，只是静悄悄少几行。

    JS 里判断空值你会写 x === null。SQL 里这么写永远匹配不到任何行。

    ❌ 错的
    SELECT COUNT(*) FROM releases
WHERE commit_sha = NULL;
-- 结果：0
    ✅ 对的
    SELECT COUNT(*) FROM releases
WHERE commit_sha IS NULL;
-- 结果：1

    原因是 SQL 用的是三值逻辑：除了真和假，还有第三个值「未知」。NULL 的语义不是「空」，而是「不知道」。两个都不知道的东西，能相等吗？不知道。所以 NULL = NULL 的结果既不是真也不是假，而是「未知」——而 WHERE 只放行结果为真的行。

    连锁反应：NOT IN 遇到 NULL 会全军覆没

    同样的道理会传染到别的地方。WHERE id NOT IN (SELECT issue_id FROM events) 看着没问题，但只要子查询里有一个 NULL，整个条件对每一行都变成「未知」，最终一行都返回不了。

    练习库里正好有两条 issue_id 为 NULL 的孤儿事件，你可以自己试。解法：改用 NOT EXISTS，或在子查询里加 WHERE issue_id IS NOT NULL。

    想一想：COUNT(*) 和 COUNT(user_id) 会不会一样大？

    不一样。COUNT(*) 数行数，COUNT(列) 只数该列非 NULL 的行数。这是判断一列有多少空值最快的办法。

    练习库实测：

    实际输出1 行
    全部行 非空 issue_id 非空 user_id 去重用户
    67 65 65 9

    67 条事件里有 2 条是孤儿（不属于任何 Issue，也没有用户）。而 COUNT(DISTINCT user_id) 是 9——这就是 TracePilot 里 user_count 想统计的东西。

    05

    ORDER BY 与 LIMIT：排序和分页

    JS
    [...issues]
  .sort((a, b) => b.event_count
                - a.event_count)
  .slice(0, 3)
    SQL
    SELECT id, event_count
FROM issues
ORDER BY event_count DESC
LIMIT 3;
    实际输出3 行
    id event_count
    iss-hydrate 24
    iss-promotion 15
    iss-address 8

    ASC 升序（默认，可省略），DESC 降序。多个排序键用逗号隔开，从左往右依次比较：ORDER BY level, event_count DESC。

    分页

    SQL
    LIMIT 20 OFFSET 0    -- 第 1 页，等价于 slice(0, 20)
LIMIT 20 OFFSET 20   -- 第 2 页，等价于 slice(20, 40)
    分页必须有稳定的排序键

    只写 ORDER BY last_seen_at 分页，如果有多行时间戳相同，它们之间的顺序是不确定的——同一行可能在第 1 页和第 2 页各出现一次，也可能一次都不出现。

    解法：排序键末尾永远追加一个唯一列，ORDER BY last_seen_at DESC, id。TracePilot 的 Issue 列表就必须这么写。

    06

    聚合函数：把多行压成一行

    对应 reduce：一堆行进去，一个值出来。

    JS
    issues.length
issues.reduce((s,i) => s+i.event_count, 0)
Math.max(...issues.map(i => i.event_count))
    SQL
    COUNT(*)
SUM(event_count)
MAX(event_count)   -- 还有 MIN / AVG
    SQL
    SELECT COUNT(*) AS 总数,
       SUM(event_count) AS 事件合计,
       ROUND(AVG(event_count), 2) AS 平均,
       MAX(event_count) AS 最多
FROM issues;
    实际输出1 行
    总数 事件合计 平均 最多
    8 65 8.13 24
    聚合函数一律跳过 NULL

    AVG 算平均时，分母是非 NULL 的行数，不是总行数。想把 NULL 当 0 算，得先转换：AVG(COALESCE(x, 0))。COALESCE 就是 SQL 版的 ??，返回第一个非 NULL 的参数。

    07

    GROUP BY：分组统计

    这是 SQL 真正开始比 JS 好用的地方。JS 里分组统计要先 reduce 出一个对象再 Object.entries，SQL 里就是一行。

    JS
    Object.entries(
  issues.reduce((acc, i) => {
    acc[i.status] = (acc[i.status] ?? 0) + 1;
    return acc;
  }, {})
).map(([status, n]) => ({ status, n }))
 .sort((a,b) => a.status < b.status ? -1 : 1)
    SQL
    SELECT status, COUNT(*) AS n
FROM issues
GROUP BY status
ORDER BY status;
    实际输出3 行
    status n
    ignored 1
    resolved 2
    unresolved 5

    规则很简单：GROUP BY 后面写什么，SELECT 里就只能出现什么，加上聚合函数。因为一个分组塌缩成了一行，没被分组的列在这一行里没有唯一值可填。

    SQLite 在这里很宽松，而这是个坑

    标准 SQL 会拒绝下面这句（title 既没分组也没聚合），MySQL 开着默认的 ONLY_FULL_GROUP_BY 也会报错。但 SQLite 照单全收，随便挑一行的 title 塞给你：

    SELECT project_id, title, COUNT(*) FROM issues GROUP BY project_id2 行
    project_id title n
    demo-project TaxError: Tax estimate request exceeded its deadline 6
    mobile-web ScrollError: Virtual list scroll anchor was lost 2

    这两个 title 是任意挑的，跟 COUNT(*) 没有任何逻辑关系——看起来像「该项目的代表错误」，其实毫无意义。这种 bug 极难发现。养成习惯：SELECT 里的每个非聚合列，都必须出现在 GROUP BY 里。

    08

    HAVING：过滤分组

    WHERE 筛行，HAVING 筛分组。区别就一条：WHERE 在分组之前跑，HAVING 在分组之后跑，所以只有 HAVING 能用聚合函数。

    JS
    grouped
  .filter(g => g.total > 10)   // ← HAVING
    SQL
    SELECT project_id, SUM(event_count) AS total
FROM issues
GROUP BY project_id
HAVING SUM(event_count) > 10;
    实际输出1 行
    project_id total
    demo-project 56

    在 WHERE 里写聚合函数会直接报错，这是一条硬规则：

    终端
    $ q "SELECT project_id FROM issues WHERE COUNT(*) > 2 GROUP BY project_id" SQL 出错：misuse of aggregate: COUNT()
    两个都能写的时候，优先写 WHERE

    WHERE 在分组前就把行扔掉了，需要分组的数据更少；HAVING 是分完组才筛。能用 WHERE 表达的条件（比如 level = 'error'）就别塞进 HAVING——结果一样，但白算了一遍。

    09

    执行顺序：为什么有些写法不行

    SQL 的书写顺序和执行顺序不一样。记住执行顺序，前面几章所有「为什么这里不能那样写」的疑问会一次性解开。

    执行顺序
    FROM / JOIN   ①  先确定数据从哪来，把表接起来
WHERE         ②  逐行过滤（此时还没分组，不能用聚合函数）
GROUP BY      ③  分组
HAVING        ④  过滤分组（此时聚合值已算出，可以用）
SELECT        ⑤  才轮到挑列、算表达式、起别名
ORDER BY      ⑥  排序（别名在这里可用，因为 SELECT 已经跑完了）
LIMIT         ⑦  最后截断

    于是那些报错都有了解释：

    • WHERE 里不能用 COUNT(*)——第 ② 步时还没分组，聚合值根本不存在。
    • ORDER BY 里可以用 SELECT 起的别名——第 ⑥ 步时第 ⑤ 步已经跑完了。
    • LIMIT 3 配 ORDER BY 是先排序再截断，不是先取 3 行再排序。
    想一想：SELECT event_count AS n FROM issues WHERE n > 8 能跑吗？

    按执行顺序，WHERE（②）跑的时候别名 n（⑤）还不存在，所以标准 SQL 里这是错的，MySQL 和 PostgreSQL 都会报 Unknown column 'n'。

    但在 SQLite 里实测能跑，而且结果正确：

    SQLite 实际输出2 行
    id n
    iss-hydrate 24
    iss-promotion 15

    这就是方言差异的典型样子：SQLite 让你养成的习惯，换到 MySQL 会当场报错。写的时候按标准来（把表达式重写一遍，或套一层子查询），别依赖 SQLite 的宽容。

    10

    JOIN：把表接起来

    关系型数据库的看家本领。前端做这件事要发两次请求再手动拼，SQL 一句话，而且是在数据旁边算的。

    JS：两次请求 + 手动拼
    const byId = new Map(
  projects.map(p => [p.id, p])
);
issues
  .filter(i => i.level === 'error')
  .map(i => ({
    id: i.id,
    level: i.level,
    project_name: byId.get(i.project_id).name,
  }));
    SQL：一句
    SELECT i.id, i.level, p.name AS project_name
FROM issues i
JOIN projects p ON i.project_id = p.id
WHERE i.level = 'error'
ORDER BY i.id;
    实际输出5 行
    id level project_name
    iss-auth error Mobile Storefront
    iss-hydrate error Checkout Web
    iss-payment error Checkout Web
    iss-promotion error Checkout Web
    iss-tax error Checkout Web

    issues i 里的 i 是表别名，之后用 i.列名 引用。两张表有同名列时（比如都有 id）必须加前缀，否则数据库不知道你指哪个。

    INNER JOIN 与 LEFT JOIN

    只有两种是日常真正要用的：

    • JOIN（即 INNER JOIN）：只保留两边都匹配上的行。要「有关联的数据」时用。
    • LEFT JOIN：保留左表全部行，右表没匹配上就填 NULL。要「包括没有关联数据的那些」时用。

    练习库里 iss-tax 是个一条事件都没有的 Issue，正好能量出两者的差：

    INNER → 65 行
    SELECT COUNT(*) FROM issues i
JOIN events e ON e.issue_id = i.id;
-- iss-tax 被丢掉了
    LEFT → 66 行
    SELECT COUNT(*) FROM issues i
LEFT JOIN events e ON e.issue_id = i.id;
-- iss-tax 保留，事件列全是 NULL

    多出来的那 1 行就是 iss-tax。由此得到一个常用套路——找「没有关联数据的行」，用 LEFT JOIN + IS NULL：

    SQL：找出一条事件都没有的 Issue
    SELECT i.id FROM issues i
LEFT JOIN events e ON e.issue_id = i.id
WHERE e.id IS NULL;   -- 右表没匹配上 → 右表的列是 NULL
    还有 RIGHT JOIN 和 FULL JOIN，但你几乎用不上

    RIGHT JOIN 就是把两张表调个位置的 LEFT JOIN，可读性更差，实务中基本不写。FULL OUTER JOIN（两边都保留）用得更少，而且老版本 SQLite 和 MySQL 压根不支持。先把 JOIN 和 LEFT JOIN 练熟，这两个覆盖 95% 的场景。

    11

    LEFT JOIN 的计数陷阱

    单独开一章，因为这是 SQL 里最经典的静默 bug，而且几乎每个人都会栽一次。

    你想统计每个 Issue 有多少事件，很自然会写 COUNT(*)：

    SQL
    SELECT i.id,
       COUNT(*)     AS 错的,
       COUNT(e.id) AS 对的
FROM issues i
LEFT JOIN events e ON e.issue_id = i.id
GROUP BY i.id;
    实际输出（节选）2 行
    id 错的 COUNT(*) 对的 COUNT(e.id)
    iss-payment 3 3
    iss-tax 1 0

    iss-tax 明明一条事件都没有，COUNT(*) 却报 1。

    原因回到上一章：LEFT JOIN 给没匹配上的左表行保留了一行，只是右表的列全填 NULL。COUNT(*) 数的是行——这一行是实实在在存在的，所以数成 1。而 COUNT(e.id) 只数右表 id 非 NULL 的行，正确地得到 0。

    记住这条规则

    LEFT JOIN 之后做计数，永远写 COUNT(右表的某个非空列)，不要写 COUNT(*)。

    这个 bug 的杀伤力在于它不报错，只是把所有「零关联」的行统计成 1。等你发现仪表盘上「0 个事件的 Issue 显示有 1 个事件」时，往往已经上线很久了。

    想一想：为什么 GROUP BY i.id 就够了，不用把 i.title 也写进去？

    因为 i.id 是主键——按主键分组，一个分组里必然只有一行 issues 记录，所以 i.title 在组内有唯一值，没有歧义。

    标准 SQL 和 PostgreSQL 认这个推导（叫函数依赖），可以只写主键。但 MySQL 的 ONLY_FULL_GROUP_BY 在某些版本里认得不完整，稳妥起见把用到的列都列上：GROUP BY i.id, i.title。多写几个字，换跨库不出事。

    12

    子查询与 CTE

    SQL 可以嵌套。括号里先算出一个结果，外层再用。

    SQL：找出事件数高于平均值的 Issue
    SELECT id, event_count FROM issues
WHERE event_count > (SELECT AVG(event_count) FROM issues)
ORDER BY event_count DESC;
    实际输出2 行
    id event_count
    iss-hydrate 24
    iss-promotion 15

    嵌套一层还好，嵌套三层就没法读了。WITH（叫 CTE，公用表表达式）把子查询提到前面命名，效果就像把一长串链式调用拆成几个有名字的中间变量：

    JS：拆中间变量
    const active = issues
  .filter(i => i.event_count > 0);

const result = active.map(i => ({
  ...i,
  pct: i.event_count / total * 100,
}));
    SQL：CTE
    WITH stats AS (
  SELECT project_id, id, event_count
  FROM issues WHERE event_count > 0
)
SELECT * FROM stats;
    CTE 是可读性最好的一次投资

    多个 CTE 用逗号串起来，后面的能引用前面的：WITH a AS (...), b AS (SELECT * FROM a) SELECT ...。复杂报表查询几乎都长这样——一层层往上搭，每层有个名字。写完自己半年后还看得懂。

    13

    窗口函数：既要明细又要统计

    GROUP BY 会把多行压成一行。但有时候你想保留每一行的明细，同时在旁边带上分组的统计值——比如「每个 Issue 的事件数，以及它占本项目的百分比」。这就是窗口函数。

    SQL
    SELECT id, event_count,
       RANK() OVER (ORDER BY event_count DESC) AS 排名,
       SUM(event_count) OVER () AS 总计
FROM issues
WHERE project_id = 'demo-project'
ORDER BY event_count DESC;
    实际输出6 行
    id event_count 排名 总计
    iss-hydrate 24 1 56
    iss-promotion 15 2 56
    iss-address 8 3 56
    iss-currency 6 4 56
    iss-payment 3 5 56
    iss-tax 0 6 56

    注意：6 行进去，6 行出来，明细一条没少，但每行都带上了「总计 56」和自己的排名。这是 GROUP BY 做不到的。

    关键字是 OVER (...)，括号里定义「窗口」——也就是这一行要跟哪些行比：

    SQL
    OVER ()                              -- 窗口 = 全部行
OVER (PARTITION BY project_id)      -- 窗口 = 同项目的行（类似 GROUP BY，但不压缩）
OVER (ORDER BY event_count DESC)     -- 窗口内排序，用于排名

    常用的几个：ROW_NUMBER() 行号（无并列）、RANK() 排名（并列后跳号）、SUM()/AVG()/COUNT() 窗口内聚合、LAG()/LEAD() 取上一行/下一行的值（算环比特别好用）。

    最实用的套路：每组取 Top N

    「每个项目里事件最多的那个 Issue」用 GROUP BY 很别扭，用窗口函数是标准解法：先用 ROW_NUMBER() OVER (PARTITION BY 组 ORDER BY 排序键) 编号，外面再套一层 WHERE rn = 1。练习 12 就是这道题。

-- 修改
UPDATE issues SET status = 'resolved' WHERE id = 'iss-hydrate';

-- 删除
DELETE FROM issues WHERE id = 'iss-hydrate';
    忘写 WHERE 会改掉整张表

    UPDATE issues SET status = 'resolved' 没有 WHERE，就是把所有 Issue 都标成已解决。DELETE FROM issues 则会清空整张表。两者都没有确认提示，也没有撤销。

    养成习惯：先把同样的条件用 SELECT 跑一遍，确认命中的行数是你预期的，再把 SELECT ... 换成 UPDATE ... SET ...。

    UPSERT：存在就跳过 / 更新

    这就是 client.ts 里 ensureDemoProject 用的写法：

    SQL
    INSERT INTO projects (id, name, dsn_key, created_at) VALUES (?, ?, ?, ?)
ON CONFLICT(id) DO NOTHING;                        -- 已存在就跳过

ON CONFLICT(id) DO UPDATE SET name = excluded.name;  -- 已存在就更新

    ON CONFLICT 后面的列必须有唯一约束（主键或 UNIQUE），否则报错——数据库需要知道靠什么判断「重复」。TracePilot 的 issues 表上有 UNIQUE(project_id, fingerprint)，事件聚合就是靠它做 UPSERT 的。

    永远用占位符，不要拼字符串

    ❌ SQL 注入
    db.prepare(
  `SELECT * FROM issues
   WHERE id = '${userInput}'`
).all();
    ✅ 参数化
    db.prepare(
  'SELECT * FROM issues WHERE id = ?'
).all(userInput);

    用了 ?，值和 SQL 是分开传给数据库的，值永远被当数据、不会被当代码解析。用户输入 ' OR '1'='1 也只是去找一个叫这个名字的 id，找不到而已。

    15

    事务：要么全成，要么全不成

    有些操作必须捆在一起。TracePilot 收到一个事件要做三件事：插入 event、更新 issue 的 event_count、更新 last_seen_at。要是第一步成了第二步崩了，数据就对不上了。

    SQL
    BEGIN;
  INSERT INTO events ...;
  UPDATE issues SET event_count = event_count + 1 WHERE id = ?;
COMMIT;    -- 一起生效
-- 出错时 ROLLBACK，就当什么都没发生过

    实测：在事务里把 demo-project 的 6 个 Issue 全改成 ignored，事务内查是 6，ROLLBACK 之后查回到 1。

    实际输出事务内 → 回滚后
    事务中: [{"c":6}] 回滚后: [{"c":1}]
    事务还能让批量写入快几十倍

    SQLite 默认每条语句都是一个独立事务，每次都要落盘。插 1000 条就是 1000 次落盘。用一个 BEGIN / COMMIT 把它们包起来，只落盘一次，通常快 1~2 个数量级。批量导数据时这是最有效的一招。

    顺带看看外键的两种删除行为

    第 1 章提过 ON DELETE CASCADE 和 ON DELETE SET NULL。实测删掉 mobile-web 项目（在事务里做的，已回滚）：

    DELETE FROM projects WHERE id = 'mobile-web'连锁反应
    受影响的表 约束 结果
    issues ON DELETE CASCADE 该项目的 2 个 Issue 被一并删除（8 → 6）
    events ON DELETE SET NULL 9 条事件保留，issue_id 被置空（孤儿事件 2 → 11）

    这正是 TracePilot 想要的取舍：聚合出来的 Issue 可以跟着项目一起消失，但用户真实上报的原始事件不能丢。

    16

    索引：为什么加一行 DDL 能快几千倍

    没有索引，数据库找数据只能从头到尾扫一遍——就像在没排序的数组里 find。索引相当于提前建好的一个 Map，代价是写入稍慢、占额外磁盘。

    EXPLAIN QUERY PLAN 能让数据库告诉你它打算怎么执行。这是排查慢查询的第一步：

    终端：走了索引
    $ q "EXPLAIN QUERY PLAN SELECT * FROM issues WHERE project_id='demo-project' ORDER BY last_seen_at DESC" SEARCH issues USING INDEX issues_project_last_seen (project_id=?)
    终端：全表扫描
    $ q "EXPLAIN QUERY PLAN SELECT * FROM issues WHERE title LIKE '%Tax%'" SCAN issues

    看两个词就够了：SEARCH = 走了索引，好。SCAN = 全表扫描，数据量大时会慢。

    第一句走的 issues_project_last_seen，就是 client.ts 里那行 DDL 建的：

    apps/server/src/db/client.ts
    CREATE INDEX IF NOT EXISTS issues_project_last_seen
  ON issues(project_id, last_seen_at);

    它的列顺序不是随便排的，正好匹配 Issue 列表页那句「WHERE project_id = ? ORDER BY last_seen_at DESC」——先按过滤列，再按排序列。这样过滤和排序能一次走完。

    索引的几条经验

    复合索引讲究顺序，遵循最左前缀。(project_id, last_seen_at) 能加速「只按 project_id 查」和「按两者查」，但加速不了「只按 last_seen_at 查」——就像电话簿按「姓, 名」排序，只知道名字是查不了的。

    LIKE '%xxx%' 用不上索引。前面带通配符等于说「不知道开头是什么」，只能全扫。要做全文搜索得用 SQLite 的 FTS5 或专门的搜索引擎。

    别无脑加索引。每个索引都会拖慢写入、占磁盘。先用 EXPLAIN QUERY PLAN 找出真正慢的查询，再针对性地加。

    17

    方言差异：SQLite 惯着你的地方

    SQL 有标准，但每家实现都有出入——就像 CSS 有标准但各浏览器有差异。SQLite 尤其宽松，它容忍的写法换到 MySQL 会当场报错。这些是本教程里实测过的差异：

    实测差异对照7 项
    场景 SQLite（你的项目） MySQL / PostgreSQL
    WHERE 里用 SELECT 别名 允许 报错
    GROUP BY 漏列 允许，任意取一行 报错（ONLY_FULL_GROUP_BY）
    外键约束 默认关闭，须 PRAGMA 打开 默认开启
    列类型 动态类型，声明 INTEGER 也塞得进字符串 严格
    日期时间 没有日期类型，本项目存毫秒整数 有 DATETIME / TIMESTAMP
    JSON 没有 JSON 类型，存 TEXT（context_json） 有原生 JSON 类型，可查内部字段
    字符串拼接 a || b PG 同；MySQL 要 CONCAT(a, b)

    时间戳存整数带来一个实际后果：想看人类可读的时间，得自己转。SQLite 的 datetime() 收的是秒，而项目存的是毫秒，所以要先除 1000：

    SQL
    SELECT version, created_at,
       datetime(created_at / 1000, 'unixepoch') AS 可读
FROM releases ORDER BY created_at;
    实际输出4 行
    version created_at 可读
    2.3.9 1770627600000 2026-02-09 09:00:00
    1.0.0 1771232400000 2026-02-16 09:00:00
    2.4.0 1771664400000 2026-02-21 09:00:00
    2.4.1 1772269200000 2026-02-28 09:00:00
    按标准写，别按 SQLite 的宽容写

    前四条差异全是「SQLite 让过、别家报错」。如果你按 SQLite 的宽松习惯写熟了，将来项目迁到 MySQL 或 PostgreSQL，会遇到一批莫名其妙的报错。把 GROUP BY 的列写全、别在 WHERE 里用别名——多打几个字，省下将来一整天的排查。
