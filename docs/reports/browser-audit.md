# 浏览器质量审查报告

## 审查目标

补足单元测试和普通 E2E 无法覆盖的真实交互检查，重点验证顶部搜索、Issue 分页、键盘焦点、
Console、主要页面和 390px 移动端布局。

审查日期：2026-08-17。

## 环境与方法

- Chrome 浏览器控制：1470 × 745，用于桌面交互、DOM、焦点、Console 和视觉检查。
- Codex 应用内浏览器：390 × 844，用于真实响应式布局和移动端交互检查。
- Playwright Chromium：执行仓库内完整 E2E，并监听 Console、页面异常和失败 API 响应。
- 虚构数据：307 个事件、16 个按稳定指纹聚合的 Issue。

## 发现与修复

### 1. 顶部搜索的行为与视觉承诺不一致

原行为会导航到 Issues 页面，再把焦点移到页面内筛选框。用户看到的是带 Command/Ctrl+K 提示的
全局搜索入口，因此自然会期待独立搜索面板，而不是页面跳转。

修复：

- 新增真正的模态搜索面板，打开时不改变当前 URL。
- 默认展示最近 8 个 Issue，输入标题或指纹后请求服务端过滤结果。
- 点击结果直接进入 Issue，Enter 打开完整筛选列表，Esc 关闭并恢复触发按钮焦点。
- 加入焦点循环、背景滚动锁定、清空和关闭按钮，以及移动端入口。

### 2. 分页存在但不可发现

原列表默认请求 25 条，而确定性种子数据只有 4 个错误根因。底部只显示两个无文字图标和 `1 / 1`，
用户无法判断列表是被截断、已经加载完，还是支持翻页。

修复：

- 默认每页 10 条，分页栏显示 `Showing 1–10 of 16 grouped issues`。
- 增加 Rows per page，可选择 10、25、50 或 100 条。
- Previous/Next 使用可见文字和无障碍名称。
- 将 307 个事件中的一部分组织为 12 个额外且稳定的错误根因，种子数据合计 16 个 Issue，默认即可
  实际翻到第二页。

### 3. 移动端搜索按钮缺少可访问名称

移动端隐藏了按钮文字和快捷键，只保留搜索图标，导致其可访问名称同时消失，语义定位无法找到该
按钮。

修复：为按钮增加稳定的 `aria-label="Search evidence"`，并在 390px 浏览器中重新验证。

### 4. 修复过程中发现指纹演示数据回归

第一次扩充种子数据时，每条事件的堆栈列号都不同。列号参与指纹计算，因此 16 个预期根因被拆成
99 个 Issue。浏览器复测通过概览数字立即暴露了这个问题。

修复：同一种根因使用固定函数和堆栈位置；重新 Seed 后 API 与页面都稳定返回 16 个分组。

## 浏览器验证结果

- 顶部按钮和 Command/Ctrl+K 均能打开搜索面板。
- 搜索面板打开后输入框获得焦点，当前页面 URL 不变。
- `hydrate` 只返回 `Checkout state failed to hydrate`，Enter 进入带 URL 参数的完整结果列表。
- Esc 关闭后焦点返回顶部搜索按钮，页面滚动锁定被正确恢复。
- 第一页 10 条、第二页 6 条；范围、总数、页码和按钮启用状态一致。
- Dashboard 的 Projects、Issues、Issue Detail、Performance、Releases 在 390px 下均无横向溢出。
- 全局搜索面板在 390 × 844 中完整位于视口内，所有按钮都有可访问名称。
- Playground 在 390px 下无横向溢出，Captured warning 和 Flush 可完成真实 SDK 上报。
- Browser MCP 检查过程中未发现非预期 Console warning/error。

## 自动化回归

`pnpm test:e2e` 当前包含 8 个 Chromium 场景，新增覆盖：

- 搜索面板不导航、结果过滤、Esc 焦点恢复和 Ctrl+K。
- 默认两页数据、第一页/第二页数量、范围文字和命名分页按钮。
- Dashboard 主要路由无 Console error、pageerror 或失败 API 响应。
