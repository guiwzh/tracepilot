## SDK 体积

```bash
pnpm measure:sdk
```

脚本会先强制执行一次 production build 再称量，因此不会误测 `dist/` 里碰巧留下的旧产物
（例如切换分支之前构建的），并复核产物确实经过压缩。同时它对结果设有预算，超出即以非零码退出，已接入 `pnpm verify` 与 CI。

报告给出两个口径，因为它们回答的是不同的问题：

| 口径                       | 压缩后 | Gzip 9 级 |   预算 |
| -------------------------- | -----: | --------: | -----: |
| 发布产物 `dist/index.js`   | 33,134 |    10,593 | 12,200 |
| 业务应用实际接入成本       | 49,225 |    16,331 | 18,800 |
| 其中 `web-vitals` 所占份额 |      — |     5,300 |      — |

**2026-10-02 链路上下文**（W3C `traceparent` 传播，见 [ADR 0013](../decisions/0013-trace-context-propagation.md)）：
产物 9,777 → 10,593 B（+816 B），接入成本 15,491 → 16,331 B（+840 B）。代价来自 `core/trace.ts`（页面浏览的 trace、
传播范围的 URL 前缀与正则匹配、traceparent 的生成与解析）和 NetworkPlugin 里 fetch、XHR 两条加头的路径。
产物离原预算只剩约 200 B，预算按实测值 +约 15% 重设为 12,200 / 18,800 B。
在事件路径上，页面里还没有请求带过 trace 时什么也不算（不生成 id、不比较页面地址）。

**2026-09-30 SDK 修订**（产物 7,321 → 9,434 B、接入成本 10,596 → 15,048 B gzip，预算按实测值 +约 15% 重设）：

| 改动                                                         | 体积代价（gzip）                                     |
| ------------------------------------------------------------ | ---------------------------------------------------- |
| `web-vitals` 换成归因版本（造成指标的元素与分段耗时）        | 接入成本 +2,346 B（2,929 → 5,275），只体现在接入成本 |
| 删掉 localStorage 保存事件                                   | 接入成本 −337 B                                      |
| 性能单独采样、请求失败判定与业务码、归因精简、指标的页面归属 | 连同删掉存储，产物合计 +702 B（7,321 → 8,023）       |
| 白屏检测（WhiteScreenPlugin）                                | 约 +0.8 KB                                           |
| 控制台面包屑（ConsolePlugin）                                | 约 +0.4 KB                                           |
| cause 链、控制台面包屑合并、`history` 包装抽成共用函数       | 约 +0.2 KB                                           |

后三行合计产物 8,023 → 9,434 B。单个插件的份额是去掉它之后重新打包的差值，gzip 不可加，只说明量级。

同日稍后，shared 的脱敏规则改为保留 `#/cart` 这样的 hash 路由：接入成本 15,048 → 15,135 B gzip（+87 B），
产物不变（shared 在产物口径里是 external）。web-vitals 份额是两次打包的差值，每次重测会有几个字节的出入。

2026-10-01 SDK 的 `captureException` 增加第三个参数 `options.fingerprint`（自定义聚合键，见
[ADR 0004](../decisions/0004-grouping-after-symbolication.md)）：产物 9,434 → 9,469 B（+35 B），接入成本 15,135 → 15,175 B（+40 B）。

同日 SDK 读取构建插件注入的 Debug ID 登记表、事件带上 `debugIds`（`core/debugIds.ts`，见
[ADR 0005](../decisions/0005-debug-ids.md)）：产物 9,469 → 9,777 B（+308 B），接入成本 15,175 → 15,491 B（+316 B），
预算不变。压缩后的产物从 5 行变成 7 行：压缩器把 `'\n'` 改写成内含真实换行的模板字符串，`measure:sdk` 判断「未经压缩」
的行数阈值因此从 5 放宽到 30（未压缩的产物有上千行且带缩进，缩进检查不变）。

2026-09-28 服务端修订把保留行列号的堆栈脱敏（`redactStack` / `redactPayload`）从 SDK 移进 shared，
服务端入库时也用它。shared 在产物口径里是 external，所以产物小了约 120 B；接入成本口径两者都含，基本不变。

**2026-09-28 SDK 修订**（产物 +1,813 B、接入成本 +2,180 B gzip），换来的是：

- **SDK 端默认脱敏**：页面地址、请求地址、面包屑与 payload 在离开页面之前就去掉查询参数与片段、
  遮蔽 token / password 等字段，规则与服务端相同（shared 的 `redaction.ts`，接入成本里约 1.1 KB 压缩后）。
  堆栈单独处理：只删帧里的查询参数，保留行列号。
- **只把会形成 Issue 的信号当事件**：成功与被取消的请求只记面包屑，性能样本不再附带面包屑；
  默认忽略 `Script error.`、ResizeObserver 循环告警与浏览器扩展报错；资源与失败请求也做短窗口去重。
- **投递**：连续失败时自动发送按指数退避并加抖动，遵守 `Retry-After`；退出时的持久化副本按标签页分开存（2026-09-30 已删除持久化）。
- **结构**：传输层由核心管理生命周期，不再是必须最后注册的插件；插件只拿到窄接口；
  新增 `reactErrorHandler`（只进产物口径，接入方不引入就被摇掉）。

体积换来的效果在网络上。同一个会话（3 次路由、5 次点击、30 个成功请求、1 个错误），在真实 Chromium 里
抓取 SDK 实际发出的内容：修订前 33 个事件、182,725 字节，其中 90% 是重复的面包屑；
修订后 3 个事件（1 个错误、2 个性能样本）、10,186 字节。

2026-09-28 库构建从 tsup 换成 tsdown 后重测，产物比 tsup 版本小约 50 B gzip。

2026-09-27 的两处变化，体积代价都显式记在这里：

- **传输层修复**（产物 +1,037 B gzip）：按字节切批与单事件裁剪、4xx 拒收不堵队、
  退出时把在途批次交给 beacon、发不完的写入 localStorage 补发（2026-09-30 已删除）。修复前后的对照见
  `tests/e2e/sdk-delivery.spec.ts`：同样 10 个带完整 breadcrumb 的错误，修复前送达 0 个。
- **改用 `web-vitals` 计算指标**（接入成本 +2,948 B gzip）：它被 external 化，
  **只体现在接入成本口径里，产物口径完全看不到**——这正是需要两个口径的又一个例子。
  换来的是 CLS 会话窗口、INP 按交互分组取高分位、LCP 首次输入后停止等官方口径。

历史数字：2026-08-31 为产物 4,639 / 接入 4,522 B gzip；首次双口径测量为 4,419 / 4,324。

**为什么要分两个口径。** 库打包工具（当时是 tsup，现在是 tsdown）默认把 workspace 依赖 external 化，所以发布产物里只留下
`import ... from "@trace-pilot/shared"`，称量产物是称不到这条依赖链的。而 shared 的 barrel
会连带引入 zod——在两个包补上 `"sideEffects": false` 之前，业务应用打包后实际付出的是
**18,763 字节 gzip（含 164 处 zod 运行时标识符）**，是产物口径的约 4.2 倍。

因此「接入成本」由一次真实打包测得：以 `apps/playground` 为解析目录（本仓库中唯一通过
workspace 依赖真实引用 SDK 的应用），用 esbuild 打包一个只调用 `createMonitor` 的入口。
脚本额外断言产物中不得出现 zod 运行时标识符，防止依赖隔离被无声破坏。

产物口径不含 Source Map 与类型声明文件。接入成本口径基于 esbuild 默认配置，
webpack / rspack 的摇树结论可能不同。

## SDK 运行时开销

```bash
pnpm measure:sdk-runtime
```

体积只说明「下载多少字节」，说明不了「跑起来要花多少」。脚本在真实浏览器里把 SDK 以
接入方的方式打包注入页面（与 `pnpm measure:sdk` 走同一条依赖解析路径），接入端点由
Playwright 路由拦截并与页面同源，避免 CORS 预检干扰测量。

测量前同样强制重新构建：SDK 的 `exports` 把 `import` 条件指向 `dist`，不重建就会安静地
测一份过期产物——连「故意破坏 teardown」这种改动都察觉不到。

| 指标                                |   P50 |     P95 | 绊线 |
| ----------------------------------- | ----: | ------: | ---: |
| `createMonitor()` + `start()`（µs） |    60 | 190–400 | 2000 |
| 单次 `captureException`（µs）       | 30–32 |   42–50 |  250 |

2026-09-30 SDK 修订后三次重跑的范围（Playwright 预装的 Chromium 141）。同一台机器上，修订前的代码（d17b4af）
与修订后的代码交替各跑三轮：

| 指标                          | 修订前 P50 / P95 | 修订后 P50 / P95 |
| ----------------------------- | ---------------: | ---------------: |
| `createMonitor()` + `start()` |  40 / 190–350 µs |  60 / 190–400 µs |
| 单次 `captureException`       | 30–34 / 44–51 µs | 30–32 / 42–50 µs |
| 重复风暴总耗时                |       3.3–4.6 ms |       3.6–3.8 ms |

初始化多约 20 µs，是新增两个插件的安装开销：包装 `console.warn` / `console.error`，白屏插件解析选择器、
注册三个监听、包装 `history`、启动第一次检测的定时器。单次采集持平：cause 链只在错误带 `cause` 时才多做事。

以下是 2026-09-28 SDK 修订时的记录，同样是 Chromium 141，但与上面不是同一台机器；更早在 Chrome 153 下测得的
旧值（初始化 10 / 50–60 µs、采集 4.5 / 9–11.5 µs）来自又一台机器，都不能直接比较。当时在同一台机器上用修订前的
代码各跑三轮做对照：

| 指标                          | 修订前 P50 / P95 | 修订后 P50 / P95 |
| ----------------------------- | ---------------: | ---------------: |
| `createMonitor()` + `start()` |  30 / 160–280 µs |  30 / 160–170 µs |
| 单次 `captureException`       |  9–10 / 20–36 µs | 24–25 / 39–55 µs |

初始化不变；单次采集约多 15 µs，是 SDK 端脱敏的代价（逐字段、逐行堆栈做正则替换，页面地址要解析 URL）。
它只在形成事件时发生：成功的请求现在只加一条面包屑，不再走完整的采集与序列化路径。
P95 波动大，是因为单批只有 10 次初始化，一次 GC 或调度抖动就会落进 P95。

单次采集比 08-31 的 4 / 7 µs 略高：事件现在在入队时就序列化一次并计算 UTF-8 字节数，
用于按字节切批；换来的是发送时不再重复序列化整批事件。

**为什么是分批计时。** 浏览器出于 Spectre 缓解把 `performance.now()` 的精度限制在约
100 µs，而单次 `createMonitor` 或 `captureException` 都远低于这个分辨率——逐次计时只会量出
「0 或 100」的量化噪声。因此测的是「一批总耗时 / 批大小」，再对多批均值取分位数：
初始化 20 批 × 10 次，采集 20 批 × 200 次。

### 错误风暴下的行为

| 场景                             | 触发 |     进入队列 |         结果 |
| -------------------------------- | ---: | -----------: | -----------: |
| 重复风暴（500 个错误 / 10 签名） |  500 |           10 | 去重挡下 490 |
| 独特风暴（签名互不相同，cap 50） |  200 | 50（达上限） |     丢弃 150 |

两个场景分开测是必要的：重复风暴里去重会把绝大多数事件挡在队列之外，队列上限根本不会
触发；只有签名互不相同时（服务端不可达 + 错误各异的最坏情况）上限才是唯一的兜底。
重复风暴占用主线程约 3.6–3.8 ms（2026-09-30，Chromium 141；09-28 同类机器上约 3 ms，此前在 Chrome 153 下
约 1.5 ms，机器不同）。

### 生命周期泄漏回归

20 轮 `start()` / `destroy()` 之后：

- **残留监听器 0 个**（与第一轮之后相比）。`web-vitals` 没有注销 API，它的监听器和
  PerformanceObserver 会存活到页面结束，所以整页只注册一次、插件实例只做订阅者；
  这些一次性的监听器在测量基线之前就已存在，断言衡量的是「是否随轮数增长」。
- 计数方法：探针在页面加载前包装 `EventTarget`，逐个记录仍然挂着的
  (target, type, handler, capture) 组合。这是判断 teardown 是否真的对称的唯一可靠方式，
  因为 `removeEventListener` 必须拿到与注册时同一个函数引用和同样的 capture 标志。
- **全局 API 全部还原**：`window.fetch`、`XMLHttpRequest.prototype.open/send`、
  `history.pushState/replaceState`、`console.warn/error` 均恢复为插桩前的引用。

这两项与机器快慢无关，因此是硬断言；三条负向测试验证过它们确实会失败：
去掉 `removeEventListener` → 报出残留 20 个；去掉 `fetch` 还原 → 报出 `fetch` 未还原；
去掉去重 → 重复风暴 400 条进入队列而非 10 条。

### 这些数字的限制

- 时间阈值是**数量级绊线**，不是性能目标，留了约 10 倍余量。它们随机器负载波动，
  不应被当作 SLA 对外引用。
- 本地用系统 Chrome、CI 用 Playwright 自带 Chromium，版本不同会影响时间数字，
  因此报告里带上浏览器版本以便归因。
- 堆用量（`heapBytesAfterCycles`）只作参考输出，不作断言：JIT 与 GC 时机让它天然带噪声。
  真正能证明「没泄漏」的是监听器计数与全局引用比对。

## 服务端微基准

```bash
pnpm benchmark
```

脚本以 1,000 个连续批次写入 10,000 个事件，每批 10 个，涉及 200 个不同用户。
所有事件归一化后**聚合为同一个 Issue**——这既贴近真实的错误风暴形态，也是接入路径的
最坏情况：任何与「Issue 内已有事件数」相关的每条开销都会在这里被放大。
随后脚本查询 Issue 列表第一页 100 次。

| 操作               |     P50 |     P95 |
| ------------------ | ------: | ------: |
| 接入一批 10 个事件 | 1.13 ms | 1.57 ms |
| Issue 列表查询     | 0.72 ms | 0.78 ms |

2026-09-28 升级依赖（better-sqlite3 13、Zod 4、Fastify 5.12 等）后，同一台机器、同一脚本三次重跑的
接入 P50 为 1.10–1.13 ms，比 09-27 的约 0.95 ms 高约 15%。尚未定位到具体是哪个依赖；
写入放大三段仍然持平，说明单条写入的开销依旧不随 Issue 内事件数增长。

### 2026-09-28 服务端修订的同机对照

修订（Source Map 缓存、编号迁移与去掉 Drizzle、时钟校正、回归重开、趋势查询）之后没有在上表那台机器上重测。
下面的数字来自另一台机器，它比上表的机器慢约 3 倍，所以只比较**同一台机器上修订前后的代码**，
各跑三次：

| 操作                                   | 修订前 P50 | 修订后 P50 |
| -------------------------------------- | ---------: | ---------: |
| 接入一批 10 个事件                     | 4.0–4.2 ms | 3.5–3.7 ms |
| Issue 列表查询（1 个 Issue、1 万事件） | 1.8–2.0 ms | 1.8–2.1 ms |

接入快约 10%：Issue 的归并从「查一次再改一次」变成一条 `INSERT … ON CONFLICT`。
列表查询持平；它的趋势查询曾对每一行重新编译同一条语句，一页 100 个 Issue（各 100 个事件）时
趋势部分 3.57 → 1.50 ms（一次性对照，不在基准脚本里）。SQLite 在进程内执行、没有网络往返，
所以「编译一次、逐个 Issue 执行」比把整页并成一条 `GROUP BY issue_id` 更快（后者 2.41 ms，
要按 Issue id 字符串排序分组）。

### 2026-10-01 先还原再聚合的同机对照

聚合改到 Source Map 还原之后（[ADR 0004](../decisions/0004-grouping-after-symbolication.md)），接入在事务之前多了一段
异步还原，Issue 改经指纹表查找。同一台机器（上一节那台较慢的机器）、同一脚本，改动前后各跑一次：

| 操作                                   | 改动前 P50 | 改动后 P50 |
| -------------------------------------- | ---------: | ---------: |
| 接入一批 10 个事件                     |    3.89 ms |    3.05 ms |
| Issue 列表查询（1 个 Issue、1 万事件） |    2.17 ms |    1.94 ms |
| 带堆栈的一批 10 个错误（30 万条映射）  |    3.75 ms |    3.72 ms |
| 重新上传并回填 2,000 个事件            |     145 ms |     173 ms |

差异都在这台机器上重复运行的波动范围内，没有可见的开销：解析结果本来就跨请求缓存，还原只是从入库之后挪到了之前。

### 2026-10-01 Debug ID 的同机对照

找 map 改为先按 Debug ID、再按版本 + 文件名（[ADR 0005](../decisions/0005-debug-ids.md)），回填多了一次按 Debug ID 的查询
和一次 `JOIN releases`。第一版每个事件都重新编译两条查找语句、在 JS 里解析整段 `context_json`，回填 2,000 个事件要
215–260 ms；改为每个连接只编译一次语句、用 `json_extract` 只取出 `debugIds` 之后，与改动前持平。同一台机器，改动前后
各跑三次（P50）：

| 操作                                   |    改动前 |    改动后 |
| -------------------------------------- | --------: | --------: |
| 接入一批 10 个事件                     | 3.07–3.33 | 3.12–3.49 |
| Issue 列表查询（1 个 Issue、1 万事件） | 1.93–2.06 | 2.05–2.15 |
| 带堆栈的一批 10 个错误（30 万条映射）  | 3.53–3.72 | 3.67–4.18 |
| 重新上传并回填 2,000 个事件            |   144–154 |   137–146 |

单位都是毫秒。基准里的 map 没有 Debug ID，测的是不用插件的应用照常工作的开销；按 Debug ID 回填的那条查询只在 map 带
Debug ID 时执行。

同日加入接入保护（[ADR 0006](../decisions/0006-ingest-protection.md)）之后，每个信封多读一次项目设置、过一遍入站过滤：
同机三次，接入一批 10 个事件 P50 2.97–3.30 ms，与上表持平。基准为了在一两秒里灌进上万个事件，关闭了限流和突增保护；
两者都是进程内存里的几次算术，没有 I/O。

### 2026-10-02 生命周期与告警的同机对照

新建、回归各多写一条活动记录（同一个事务），接入之后多一次恶化检查和一轮告警分发（[ADR 0010](../decisions/0010-issue-lifecycle-and-alerts.md)）。
第一版在接入请求里同步跑分发器的第一段、每轮重新编译语句，最坏情况（基准的「带堆栈」一批 10 个事件，每个事件都按不同的
源码位置聚合成一个新 Issue）P50 从约 4.1 ms 涨到 5.0–6.3 ms。改了三处之后回到波动范围附近：

- 恶化检查和分发移到响应返回之后的下一轮事件循环；
- 活动记录只有在项目有启用的规则订阅了它时才进入「待处理」，没有配置告警的项目不必为每个新 Issue 多一轮分发；
- 分发器和恶化检查的语句只编译一次。

同一台机器，改动前后交替各跑两到四次（P50，毫秒；这台机器比上面几节测量时慢）：

| 操作                                       |    改动前 |    改动后 |
| ------------------------------------------ | --------: | --------: |
| 接入一批 10 个事件（同一个 Issue）         | 3.36–3.64 | 3.55–3.72 |
| Issue 列表查询                             | 2.24–2.37 | 2.25–2.27 |
| 带堆栈的一批 10 个错误（每个都是新 Issue） | 4.08–4.26 | 4.27–4.53 |
| 重新上传并回填 2,000 个事件                |   145–161 |   145–149 |

真实流量里新 Issue 很少，绝大多数事件归入已有的 Issue，走的是第一行的路径。

### Source Map 还原

基准的 `sourceMap` 一节生成一份 30 万条映射（2.4 MB）的 map，上传后接入 2,000 个带三帧堆栈的错误，
再重新上传一次（回填这 2,000 个事件）。同上，数字来自那台较慢的机器，修订前后同机对照：

| 操作                             | 修订前 |      修订后 |
| -------------------------------- | -----: | ----------: |
| 带堆栈的一批 10 个错误，接入 P50 | 232 ms |      3.8 ms |
| 重新上传并回填 2,000 个事件      |   44 s | 0.14–0.20 s |
| 首次上传（含校验）               |  56 ms |    63–71 ms |

修订前每还原一个事件就把整份 map 读一遍、解析一遍；现在解析结果按文件缓存在进程里（上限按 map 原始大小
计 32 MB），接入、回填和排障 Agent 共用。首次上传多出的约 10 ms 是落盘前把每一条映射都解码一遍：
mappings 损坏的 map 曾以 201 通过上传，之后该版本每一次带堆栈的接入都返回 500。

### 写入放大

`ingestWriteAmplification` 按接入进度分三段统计单批延迟，用来验证单条写入的开销
**不随 Issue 内已有事件数增长**：

| Issue 内已有事件 |     P50 |     P95 |
| ---------------- | ------: | ------: |
| 1,000            | 1.26 ms | 2.00 ms |
| 5,000            | 1.13 ms | 1.31 ms |
| 10,000           | 1.10 ms | 1.23 ms |

三段基本持平。若尾段明显高于首段，说明接入路径上又出现了与已有事件数成正比的操作。

**改动前的对照**（2026-08-31，同一台机器）。早期实现对每条入库事件都用 `COUNT(*)` 与 `COUNT(DISTINCT user_id)`
重新派生 Issue 计数，单次写入退化为 O(Issue 内事件数)。同一脚本在同一台机器上的结果：

| Issue 内已有事件 | 改动前 P50 | 改动后 P50 |
| ---------------- | ---------: | ---------: |
| 1,000            |    1.79 ms |    1.14 ms |
| 5,000            |    6.57 ms |    0.96 ms |
| 10,000           |   12.88 ms |    0.98 ms |

改法：幂等已由前置的 `eventId` 去重保证（重复批次在插入前就跳过了），因此计数改为增量
累加；`user_count` 仅在该用户首次出现于此 Issue 时 +1，判定走 `(issue_id, user_id)` 索引。
该判定必须在事件落库**之前**执行，否则会查到刚写入的这一行，`user_count` 将恒为 0；
`app.test.ts` 中有一条回归测试专门锁定这个顺序。

### 与历史数字的口径差异

2026-08-12 的基线记录的是「接入 P50 1.88 ms / Issue 查询 P50 0.13 ms」，样本量是 1,000 个
事件。本次把基准放大到 10,000 个事件后，两个数字都不能与旧值直接比较：

- **接入延迟**下降，是计数器改动的结果。
- **Issue 列表查询**从 0.13 ms 升到 0.75 ms，**不是回退**，而是数据量变成 10 倍所致。
  在同一份 10,000 事件数据上，计数器改动前后分别测得 0.71 ms 与 0.69 ms，基本无差异。
  列表查询会为每个 Issue 单独查一次趋势桶（语句只编译一次），且趋势窗口内的事件全部参与计数，
  因此该数字随单 Issue 事件数增长——这是当前已知限制。

## 图表更新策略

```bash
pnpm measure:chart
```

`Chart.tsx` 原先把实例创建和数据更新写在同一个 effect 里，依赖数组是 `[option]`——
option 引用一变就 dispose 再 init。而上游的 `useMemo` 依赖 React Query 的 data，
每次 refetch 都产生新引用，于是**每轮轮询所有图表整体重建**。改造后拆成两个 effect：
`[]` 只管 init/dispose，`[option]` 只调 setOption。

一屏 5 个图表（三系列柱状 + 折线 + 三个环形饼图，对应 Performance 页与 Issue 详情页的
真实构成），每轮轮询各更新一次，取 15 轮的分位数：

| 策略                     | 每轮轮询 P50 |     P95 | 300 次更新中新建的 canvas |
| ------------------------ | -----------: | ------: | ------------------------: |
| 改造前（dispose + init） |      2.34 ms | 3.46 ms |                     1,500 |
| 改造后（仅 setOption）   |      1.25 ms | 1.73 ms |                     **0** |

同步开销约降到一半，但**更有意义的是 canvas 那一列**：改造前每轮轮询都在丢弃并重建全部
画布，改造后一个都不新建。

### 这个数字的限制

- **这是两种模式的隔离复现，不是端到端页面测量。** 改造前的代码已经不在仓库里，临时回退
  再测的结果无法由命令复现，所以在同一页面、同一份 option 形状下并排跑两种策略。
  真实组件确实按「复用」方式工作，由 `tests/e2e/chart-instance-reuse.spec.ts` 保证——
  它断言容器内的 canvas 节点在 option 变化后保持同一引用。
- **测量关闭了动画，只反映 setOption 的同步开销。** 真实图表是有动画的：重建策略下每轮
  轮询都会重放一次入场动画，那部分 rAF 工作和肉眼可见的闪烁不在这个数字里——
  所以实际差距比 1.9 倍更大。
- 脚本里的硬断言校验的是**对照本身是否成立**（复用组确实没有重建），不是组件的回归保护。

## 解读限制

**表里的时间数字是某一次运行的快照。** 重跑 `pnpm benchmark` 或 `pnpm measure:chart`
会得到相差百分之几的值（例如 2026-09-28 三次重跑的接入 P50 在 1.10–1.13 ms 之间），这是机器负载与 JIT
状态的正常波动，不是回归。体积数字则是确定性的，同一次构建重复称量结果完全一致。
需要判断「是否退化」时看的是脚本里的预算与绊线，不是与表中数字逐位比对。

这是一个确定性的开发基线，适合发现明显的性能回退，但并非负载测试：它不包含 HTTP 网络、并发
写入竞争、身份认证、远程磁盘、模型调用或生产遥测数据分布。请勿将这些数值用作容量或 SLA 声明。
生产指标必须注明机器配置、并发计划、预热过程、多轮运行、原始样本和联网部署环境。
