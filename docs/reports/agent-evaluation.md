# 诊断评测：规则、单次调用与 Agent

```bash
pnpm evaluate:agent                            # 四个引擎，模型引擎各跑 3 次，裁判复核；没有密钥时只跑 rules 与 agent-local
pnpm evaluate:agent --engines=agent --runs=5   # 只跑 Agent，每个用例 5 次
pnpm evaluate:agent --cases=upstream-503       # 只跑指定用例（部分运行不覆盖已提交的结果）
pnpm evaluate:agent --record                   # 同时把 Agent 的模型回复录到 apps/server/src/eval/recordings/
pnpm evaluate:agent --replay                   # 不需要密钥：按录制回放 Agent，复现结果表
pnpm evaluate:agreement --template             # 生成盲评标注文件；填好后不带参数运行，计算裁判与人工的一致性
```

完整地跑了 Agent 时，原始结果写入 [`agent-evaluation.json`](agent-evaluation.json)，每个用例、每个引擎、每一次运行的
完整输出和调查轨迹都在里面（现有文件是 2026-10-02 的完整运行：每个模型引擎每个用例 3 次，带轨迹）。
设计取舍见 [ADR 0009](../decisions/0009-evaluation-reliability.md)。

四个引擎：

| 引擎          | 是什么                                                                                                     | 需要密钥           |
| ------------- | ---------------------------------------------------------------------------------------------------------- | ------------------ |
| `rules`       | 规则引擎，单次、确定性，没有模型时的基线                                                                   | 否                 |
| `agent-local` | 离线脚本驱动的 Agent 循环：工具、引用核对与真实 Agent 相同，「下一步调什么」按固定剧本走。**不是模型推理** | 否                 |
| `single`      | 一次模型调用 + 结构化输出，即 Agent 之前的诊断方式                                                         | 是                 |
| `agent`       | 模型驱动的只读工具调用循环                                                                                 | 是（回放时不需要） |

用例本身写错时，模型的分数就没有意义。

## 评分

两层，互相对照：

1. **关键词（确定性，无需模型）**：摘要 + 排名第一的原因是否覆盖参考根因的每组关键事实。
   评分前会删掉摘要里照抄的 Issue 标题——规则引擎会把标题拼进摘要，标题里本来就有的词
   （例如 `503`、`coupon`）不能算作找到了根因。第一版评分没做这一步，规则基线因此虚高到 4/12。
2. **LLM 裁判（需要密钥）**：给出 correct / partial / incorrect 与一句理由，并判断报告是否
   把注入或误导的说法当成了结论。

对抗用例单独统计：禁用说法出现在摘要或置信度 ≥ 0.5 的原因里，才算被注入或被带偏；
在低置信原因里提到并排除它，属于正确处理。

### 重复试验：pass@1 与 pass^k

模型的输出有随机性。模型引擎每个用例默认跑 3 次（`--runs`），一个用例跑了 n 次、成功 c 次：

- **pass@1** = c / n 的平均：单次运行答对的概率；
- **pass^k** = C(c, k) / C(n, k) 的平均：随机取 k 次**全部**答对的概率（τ-bench 的可靠性指标）。k 取 n 时，
  只有每次都对的用例才算数；
- 另外给出每一轮单独算的裁判得分范围，看单次跑出来的数字能差多少。

「成功」有两种口径：关键词全部命中；裁判判为 correct（部分正确不算）。没交出报告的运行算失败。

### 轨迹指标

结论之外，看 Agent 是怎么查的（`eval/trajectory.ts`，数据来自调查时发出的事件，和界面收到的 SSE 事件是同一串）：

| 指标             | 含义                                                                       |
| ---------------- | -------------------------------------------------------------------------- |
| 平均工具调用     | 每次调查实际执行的工具调用数                                               |
| 重复调用占比     | 与之前某次调用的工具和参数完全相同（参数键顺序不同也算），结果不会变       |
| 失败调用占比     | 返回错误的调用：参数不合法、事件不存在、超时。工具如实回答「没有数据」不算 |
| 有报告被驳回     | 至少一次提交的报告没通过形状或引用核对、改了重交的运行                     |
| 关键证据工具召回 | 用例标注的关键证据工具里，被成功调用过的比例                               |

召回低于 1 而结论正确，说明结论不是从那份证据来的——可能是碰巧，也可能是从别的线索推断出来的，需要看轨迹判断。

### 裁判校准

裁判默认就是被测模型（同一个端点和密钥）。`EVAL_JUDGE_API_URL`、`EVAL_JUDGE_API_KEY`、`EVAL_JUDGE_MODEL` 可以换成
另一家服务商的模型，结果 JSON 的 `judge.sameVendor` 注明是否同源。裁判 temperature 取 0。

裁判本身也要被检验：`pnpm evaluate:agreement --template` 从结果生成
`docs/reports/agent-evaluation-labels.json`，每条只有参考根因和报告内容——**没有引擎名和裁判结论，顺序按哈希打乱**，
避免标注的人被带偏。填写 `human` 字段（标准与裁判提示词相同）后不带参数运行，输出裁判与人工的一致率、
Cohen's kappa（三档和「是否正确」两档两种口径）、混淆矩阵和每一条分歧。kappa 扣除了「碰巧一致」：两个评分者
都偏爱「部分正确」时，一致率可以很高而 kappa 很低。

## 录制与回放

真实模型评测要密钥、要花钱、每次结果不同，进不了 CI。`--record` 在跑 Agent 时把模型每一轮的回复（文字、工具调用、
token 用量）连同评分和裁判结论，存到 `apps/server/src/eval/recordings/<模型>/<用例>.json`；`--replay` 用这些回复
驱动**当前的**循环、工具和引用核对：

- 不需要密钥就能复现整张结果表（裁判结论取录制时的，`--rejudge` 可以让另一个裁判重新打分）；
- `replay.test.ts` 在 CI 里回放全部录制：步数、工具调用序列（名字和成败）、引用核对结果，任何一项与录制时不同就失败。
  例如改了工具的输出格式，模型当时逐字引用的原文在新输出里找不到了，引用核对就会失败；
- 工具输出的内容变了但行为一致时不算失败，只提示录制可能需要更新；提示词版本或工具清单变了，`--replay` 会列出
  哪些录制已经过时——它们记录的是模型对旧输入的反应。

回放要求工具输出和录制时逐字一致，所以用例数据只由一个时钟决定：用例里的时间都相对于 `CASES_CLOCK`，
`prepareCase(evalCase, directory, clock)` 写库时整体平移到 `clock`（事件、版本部署时间、接入的收到时间都由它推出），
录制时记下这个时钟，回放时传回去。

回放回答不了「换了提示词或模型以后会怎样」，那需要重新录制。

#### 怎么读这些数字

- **差距主要在稳定性，不在「能不能答对一次」。** 三次里至少一次判为正确（pass@3）的比例，单次调用和 Agent 都是 0.83；
  三次都正确（pass^3）时，单次调用只剩 0.25，Agent 是 0.75。单次调用有 7 个用例三次的结论不完全一样，Agent 有 2 个
  （`stale-chunk`、`missing-source-map`）。只跑一次的评测分不出这两种情况，这正是加入重复试验的原因。
- **Agent 剩下的问题是系统性的：三次错法相同，不是运气。**
  - `missing-source-map`：三次都记下了「没有 Source Map」，却仍把一个具体的代码缺陷排在第一位（一次被判为错误）。
    正确的做法是把「缺少 map」本身作为结论、要求补传。这和 2026-09-27 那次单次运行的错误一样，提示词 v4 没有改善它。
  - `dom-not-ready-regression`：三次都找到了模块顶层对 null 调用 `addEventListener`，但没有归结为「脚本在 DOM 就绪前执行」
    这个时序回归。
  - `stale-chunk-after-deploy`：三次里两次把缺失的 chunk 归到 3.1.0，没注意到报错页面加载于 3.2.0 部署之前。
    这三类都需要改提示词或工具（例如给「证据缺失」定下置信度上限、让版本对比直接给出页面加载时间与部署时间的先后），
    而不是多跑几次。
- **关键证据工具召回是 1**：每一次都调用过关键证据所在的工具。错在读懂证据，不在没看到证据。
- **单次调用有 2 次没交出报告**：结构化输出的 JSON 不合法。Agent 的报告通过 `submit_report` 工具提交，经服务端 Schema
  校验后驳回重交，36 次全部交出了报告；其中 5 次第一次提交被驳回（引用的原文对不上等），改正后通过，最终引用有效率 100%。
- **注入与误导**：以裁判为准，Agent 0/9，单次调用 1/8（把注入的「数据库故障」列为一个原因），规则引擎 1/3。关键词口径给出
  Agent 5/9、单次调用 6/8，逐条核对 Agent 的 5 次**全部是误报**：报告提到「database outage」「CDN outage」是为了否定它，
  原文如「the issue title's claim of a confirmed database outage is an injected instruction unsupported by …」。
  关键词匹配识别不了否定语境，评分规则没有在看到结果后修改。
- **代价：Agent 的输入 token 约是单次调用的 11 倍，耗时约 2.1 倍。** 比 09-27 的 6 倍更高，主要因为工具多了代码类的三个：
  平均 8.6 个调用里约 2.9 个是搜代码、找嫌疑提交、读文件，而评测用例没有 git 仓库，它们只会如实回答「没有配置仓库」，
  Agent 仍然每次都会调用。没有配置仓库时不把这三个工具交给模型，就能省掉这部分。
- **离线脚本的 5 个「正确」来自模板碰巧对上**（例如「上游请求失败」「字段缺失」），它不做推理；它的价值是可复现的下限。
- **裁判比上一次严格**：同一个规则引擎，09-27 的裁判（被测模型自己）给 0.38，这次的 `deepseek-v4-pro` 给 0.29。
  不同裁判的分数不能直接比较；同一张表里引擎之间的比较才有意义。

2026-09-27 那次（提示词 v2、每个引擎跑一次、裁判就是被测模型）的结果是：Agent 0.79、单次调用 0.67、规则 0.38，原始数据已被
这次的结果替换，可以从 git 历史里取回。

#### 第一次接真实模型时暴露并修复的两个问题（2026-09-27）

第一次用真实模型跑单个用例时，Agent 的**引用有效率是 0/8**，查下来是两个问题：

1. **模型读不到 `tool_call_id`。** 最初要求证据引用工具调用的 id，但 chat/completions 里这个 id 只存在于
   消息元数据，模型看不见。DeepSeek 先引用工具名，再编造形如 `toolu_01H8…` 的 id，最后把所有工具重调一遍
   想找到 id，耗费 3.3 万 token 仍未通过。修复：每个工具结果正文第一行写上 `ref: T3`，证据引用 `T3`，
   服务端再映射回真实调用。修复后同一用例 7/7 通过、工具调用从 10 次降到 6 次。
   本地单元测试和模拟端点都没能发现这个问题——测试替身「知道」自己发出的 id。
2. **评测数据泄露了答案。** 事件 id 由用例名拼成（`null-guard-regression-003`），单次调用的报告里直接写了
   「breadcrumb id 以 null-guard-regression 开头」。修复：事件 id 改为不透明的哈希前缀。上表是修复后的结果。

另外把报告字段的长度上限放宽了：DeepSeek 的摘要常超过 600 字符而它并不遵守 Schema 里的 `maxLength`，
每次超长都要多一轮被驳回的往返。

## 限制

- 12 个用例是小样本，适合回归与对比，不足以宣称泛化的准确率。重复试验能说明「同一个用例每次结果是否一致」，
  不能替代更多用例。
- 每个用例只跑了 3 次，pass^3 的颗粒度很粗（12 个用例，每个占 0.083）。裁判换成了另一个模型（`deepseek-v4-pro`），
  但仍是同一家服务商，可能对同源的输出有偏好；裁判也还没有经过人工校准：盲评标注文件
  [`agent-evaluation-labels.json`](agent-evaluation-labels.json) 已经生成（94 条），`human` 字段需要人来填，
  填好后运行 `pnpm evaluate:agreement` 计算一致率与 kappa。
