# ADR 0010：Issue 生命周期与告警——回归、恶化、发件箱分发到 Webhook / Slack / 飞书 / 钉钉

- 状态：已采纳
- 日期：2026-10-02

## 背景

监控的价值一半在「出事时有人知道」。之前的 TracePilot 只能等人打开工作台：新问题、已解决的问题又出现、老问题突然变多，
都不会主动通知任何人；Issue 也只有未解决、已解决、已忽略三种状态，看不出「它是刚回归的」还是「正在恶化」。

行业做法：Sentry 的 Issue 有细分状态（new / ongoing / regressed / escalating，忽略分为「永久」和「直到恶化」），恶化
以 Issue 自己的历史为基线；告警规则由触发条件、过滤、动作和 action interval（同一个 Issue 多久最多通知一次）组成。
国内团队普遍用飞书、钉钉群机器人收告警，它们的自定义机器人都支持签名校验。

## 决策

1. **细分状态**：`issues.substatus` 记 regressed、escalating、until_escalating（忽略到恶化为止），人改状态时清除。
   「new」不存：出现时间本身就能判断。
2. **活动记录即发件箱**：新建、回归在接入的同一个事务里写一条 `issue_activity`，恶化由恶化检测写，状态变更和合并由人的
   操作写。告警分发器从待处理的记录里取，生成通知、发送、重试。Issue 变了就一定有通知（事务性发件箱），发通知的网络请求
   不在接入路径上。活动记录同时就是 Issue 详情里的时间线。
3. **恶化 = 最近一小时 ≥ max(20, 5 × 过去 7 天平均每小时)**，只看未解决的和「忽略到恶化为止」的、且出现超过一天的 Issue。
   接入后检查，每个 Issue 每分钟最多一次。
4. **规则**：触发条件（新 Issue / 回归 / 恶化）、级别下限、渠道、每个 Issue 的去重间隔（默认 60 分钟，不分触发条件）、
   静默到某个时间；另有每条规则每小时 20 条的上限。被抑制的通知也记下原因。
5. **渠道**：通用 Webhook（HMAC-SHA256 签名「时间戳.请求体」）、Slack Incoming Webhook、飞书与钉钉自定义机器人（各按
   官方文档的算法签名，并检查响应体里的错误码）。Slack、飞书、钉钉只接受官方域名；不跟随重定向；用户能控制的文本转义后
   再放进消息，防止 @所有人。
6. **至少一次投递**：失败从 30 秒起指数退避，最多 5 次；每条通知带 `x-tracepilot-delivery`，接收方可以去重。

## 替代方案

- **接入时直接发通知**：最简单，但发通知的网络请求会拖慢接入、或在事务外丢失（进程在提交后、发送前崩溃）；也没有重试。
- **消息队列（Redis、Kafka）**：多实例时是正解；单机 SQLite 部署里，表就是最可靠、最好解释的队列。迁到队列时，
  活动记录的「待处理」就是要投递的消息。
- **全局阈值告警（每分钟超过 N 个）**：一个阈值对所有 Issue 都不合适：小问题翻二十倍也到不了，大问题日常就超过。
  恶化要以 Issue 自己的常态为基线。
- **Sentry 式的逐日预测**：更精细，但要几周的数据和更复杂的模型；5 倍常态的规则好解释、好测，昼夜周期由倍数留出余量。
- **只做通用 Webhook**：最通用，但国内团队真正用的是飞书和钉钉群，它们要特定的消息格式和签名，接入成本应该由我们承担。

## 影响

- 新增 3 张表和 2 个列（迁移 7）；接入事务里新建、回归时多写一行，正常事件不受影响。活动记录只在有规则订阅时才进入
  「待处理」，恶化检查和分发在响应返回之后进行：同机对照，普通接入在波动范围内，每个事件都是新 Issue 的最坏情况慢约 6%。
- 进程内多一个每 5 秒一轮的分发器，关闭时等这一轮结束；没发出的通知留在库里。
- 渠道凭据明文存在本地库里，接口只回显打码的地址；改渠道要删掉重建。
- 通用 Webhook 可以指向任意地址，而管理接口没有鉴权：部署到公网之前要加鉴权和目标允许列表（列入已知限制）。
- A4（告警触发自动调查）建立在这套规则和活动记录之上。
