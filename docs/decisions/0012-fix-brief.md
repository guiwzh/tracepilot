# ADR 0012：TracePilot 不改代码，只把调查整理成交给编码 Agent 的修复简报

- 状态：已采纳
- 日期：2026-10-02

## 背景

调查回答了「哪里坏了、为什么」，下一步是改代码。业界有两条路：Sentry 的 Seer 等产品直接生成补丁、开 PR；另一条是把上下文
交给开发者已经在用的编码 Agent（Claude Code、Cursor），由它在本地仓库里改、跑测试。

TracePilot 的位置决定了它不适合改代码：它在生产侧，读的是任何人都能伪造的遥测；它没有、也不应该有仓库的写权限和 CI；
而开发者的编码 Agent 就在仓库旁边，能读完整代码、跑测试、由开发者审查每一处改动。

## 决策

1. **只生成修复简报**：问题、最可能的根因与其他候选、证据（标出哪些引用核验过）、调查读过的代码位置、嫌疑提交、建议方向、
   还缺什么、怎么动手（先写复现失败的测试，再做最小修改）。数据取自完成的报告和这次调查的事件日志，不重新执行工具。
2. **三处出口**：REST（按运行或按 Issue 取）、工作台一键复制、MCP 的 `get_fix_brief` 工具与 `fix_issue` 提示词。
3. **把简报当作注入面**：编码 Agent 有写文件、跑命令的权限，简报里却有可伪造的生产文本。来自生产的原文全部放进代码块，
   围栏长度超过内容里最长的反引号串；开头声明代码块里是数据；模型写的分析单独成节、注明需要核对，压成一行防止伪造章节；
   标题只放 Issue 的短 id。

## 替代方案

- **直接生成补丁 / 开 PR**：需要仓库写权限、CI 和对整个代码库的理解；补丁来自读了不可信遥测的模型，审查负担转嫁给开发者，
  还多了一条「伪造上报 → 自动 PR」的攻击路径。
- **只给报告，不做简报**：报告是给人看的（引用、置信度、工具调用的跳转），编码 Agent 需要的是可执行的上下文——代码位置、
  提交、复现步骤，以及「哪些是数据」的明确边界。
- **把报告原样塞进提示词**：遥测里的指令会和真正的任务混在一起，编码 Agent 分不清。

## 影响

- 工作台与 MCP 各多一个入口；MCP 工具变为 12 个、提示词 2 个。
- 简报的质量上限是调查的质量：离线脚本跑出的简报如实标注「不是模型推理」。
- 简报的格式约束（围栏、单行化）在单元测试里用伪造的标题和伪造的章节验证。
