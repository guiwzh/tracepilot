# ADR 0008：排障 Agent 读被监控应用的 git 仓库——按版本读代码、搜代码、找嫌疑提交

- 状态：已采纳，扩展 ADR 0003 的工具集（5 个 → 8 个只读工具）
- 日期：2026-10-01

## 背景

排障 Agent 原来能看到的代码只有 Source Map 内联的、出错行前后 5 行（`get_source_context`）。很多根因不在这几行里：

- 字段为什么会缺：要看类型定义（`summary?: CartSummary` 本来就是可选的）、看数据从哪来；
- 为什么从这个版本开始：要看这个版本相对上个版本改了什么。

前端问题的高发场景正是「发版引入」。行业里的做法：Sentry 把 Issue 关联到「可疑提交」（最早按版本范围加堆栈文件匹配，
后来改用 blame），Seer 读代码库做根因分析；Datadog 的 Bits AI 也读代码与变更。

## 决策

1. 新增三个只读工具，与其余工具同一个注册表（Agent 和 MCP 都能用）：
   - `read_source_file`：某个版本发布时的文件内容，一次最多 80 行；
   - `search_code`：那个版本的代码里按字面搜索，最多 20 条；
   - `find_suspect_commits`：问题首次出现的版本与前一个版本之间的提交（标出改过堆栈文件的），加上对栈顶应用帧的
     `git blame`，两个信号互相印证。
2. 版本 → 提交：`releases.commit_sha`。构建插件创建版本时自动记下 `git rev-parse HEAD`；手动创建时可以填。
3. 仓库在本机：`REPOSITORY_ROOT/<项目 id>`，由部署者克隆或链接；**不提供接口设置路径**。
4. 只调用 git 的读命令（`show`、`grep`、`log`、`blame`、`ls-tree`、`rev-parse`），`execFile` 传参数数组，路径与提交号
   严格校验，关闭会执行外部程序的 git 配置，5 秒超时。
5. 源码外发受 `AGENT_SOURCE_CONTEXT` 同一个开关控制；关闭时嫌疑提交只给元数据。
6. 演示数据配一个真实的 git 仓库：主问题由 2.4.1 之前的一个提交引入，离线调查脚本会引用它（证据来源 `commit`）。

## 替代方案

- **对接 GitHub / GitLab API**：要令牌、要处理网络和限流，本地演示跑不起来；而 git 的读命令在任何托管平台上都一样。
  可以作为后续的另一种仓库来源。
- **只靠 Source Map 的 sourcesContent**：只有被打包进来的文件、只有那个版本，看不到类型定义以外的文件，也看不到历史。
- **只用 blame**：出错行没变、改的是上游的数据（例如另一个文件不再填 `summary`）时找不到；版本范围的提交列表能补上。
- **只用版本范围**：一个版本里几十个提交时噪声太大；blame 能把范围缩到改过出错行的那一个。
- **允许通过接口配置仓库路径**：管理接口没有鉴权，这等于允许读服务器上的任意目录。

## 影响

- 调查能回答「哪个改动引入的」，报告里可以有指向提交的证据；提示词要求把提交当线索，说明证据如何把它和失败联系起来。
- 服务端需要 `git`，仓库要事先放到本机并包含版本的提交；没有时工具如实回答（`NO_REPOSITORY`、`NO_COMMIT`、
  `COMMIT_NOT_FOUND`），调查照常进行。
- 嫌疑提交是启发式的；map 路径按后缀对到仓库文件，有多个同名候选时放弃。
- 提示词版本升到 `investigation-v3`。
