# ADR 0006：接入保护——入站过滤、进程内限流与突增保护、上报去向计数

- 状态：已采纳
- 日期：2026-10-01

## 背景

接入接口只认 DSN Key，而 DSN Key 写在浏览器代码里，不是密钥。三类上报原来都会原样进库：

1. **不是应用自己的问题**：浏览器扩展注入的脚本报错、搜索引擎爬虫和监控探针的访问、本地开发时的上报。SDK 会过滤一部分，
   但旧版本 SDK、别人写的上报代码、伪造的请求都不经过 SDK；SDK 的规则要等业务方发版才能改。
2. **量失控**：一次发版带进一个死循环里的报错，几分钟就能刷出平时几天的量。服务端要为同一个 Issue 写几万行，同一时间
   真正的新问题被淹没；单机 SQLite 是所有项目共用的，一个项目打满，别的项目也接不进来。
3. **恶意或配错的高频上报**：拿到 DSN Key 就能刷。

另外，任何丢弃都必须看得见：Issue 列表里的数字比真实发生的少，却没人知道少了多少，比不丢更难排查。

## 决策

1. **入站过滤**（服务端、按项目设置）：浏览器扩展（只看栈顶帧）、爬虫 User-Agent（性能样本也过滤）、localhost（默认关）、
   错误消息与版本的通配符规则。规则与 Sentry 的 Inbound Filters 相同。被过滤的事件不入库、不占限流额度。
2. **限流**：每个项目一个令牌桶，每分钟 N 个（默认 6,000，项目可单独设），最多攒 10 秒的量且不少于一个满信封。
3. **突增保护**：这一分钟收下的事件超过「过去一小时每分钟平均 × 10」且超过 600 个时，拒收到这一分钟结束。基线只计收下的
   事件，持续的新常态在一小时里逐渐被接受。
4. 拒收的信封整个返回 **429 + Retry-After**，什么都不写；SDK 已经按 `Retry-After` 退避、队列有上限。
5. **上报去向**（收下、被过滤、被限流，及原因）在内存里按「项目 + 小时」累加，每 10 秒合并写入 `ingest_outcomes`；
   工作台的 Settings 页展示最近 24 小时，并可修改项目设置。
6. 限流状态在**进程内存**里，不引入 Redis。

## 替代方案

- **只靠 SDK 过滤和采样**：改规则要业务方发版；挡不住不经过 SDK 的上报。SDK 侧的过滤保留，服务端是第二道。
- **固定窗口计数**（每分钟清零）：窗口边界前后各打满一次就是两倍的瞬时量；令牌桶对突发的约束是连续的。
- **只用固定上限、不做突增保护**：上限要为量最大的时段留余量，平时就形同虚设；突增保护按项目自己的常态判断。
- **超限时部分接收、丢掉其余**（Sentry Relay 的做法之一）：SDK 不知道哪些被丢了，也就不会退避。整批 429 让 SDK 自己按
  `Retry-After` 等待，队列满了在客户端丢弃，服务端不必为注定要丢的事件做还原和聚合。
- **每个请求写一行去向**：接入是写入最频繁的路径，多一次写就多一次落盘；内存聚合后定期写，代价是崩溃时丢不到 10 秒的计数。
- **Redis 计数**（`INCR` + 过期时间，或 GCRA）：多实例部署时必须，单进程的 MVP 不需要多一个服务。见已知限制。

## 影响

- 被过滤的事件和被限流的批次都有据可查；Issue 计数与真实发生的差额在 Settings 页上看得到。
- 管理类接口（包括新增的设置接口）仍无鉴权。
- 多实例时每个实例各算各的限额，总量变成 N 倍；进程重启后突增基线从零开始，这段时间按下限判断。
- 基准脚本关闭了限流和突增保护（`INGEST_RATE_LIMIT_PER_MINUTE=0`、`SPIKE_PROTECTION=false` 的等价配置），测的是接入本身。
