# ADR 0003：只读排障 Agent 与逐条核验的引用

- 状态：已采纳，部分取代 ADR 0002 的诊断流程
- 日期：2026-09-27

## 背景

ADR 0002 的诊断是一次模型调用：服务端预先挑好证据（最近 8 个事件、每个 12 条 Breadcrumb、
压缩或还原后的栈），模型只能在这份固定快照上推理。两个问题：

1. 模型看不到快照之外的信息。出错行的源码、问题是否只在某个版本出现，都要人预先猜到并塞进去。
2. 「每条原因都能回指证据」只由提示词和 Schema 约束，引用的内容是否真的存在，没有检查。

## 决策

诊断改为工具调用循环，模型自己决定查什么，但只能通过 5 个只读工具：

| 工具                 | 作用                                                        |
| -------------------- | ----------------------------------------------------------- |
| `get_issue_overview` | 计数、首末次出现、浏览器/路由/版本分布                      |
| `list_event_samples` | 最近事件及其 id                                             |
| `get_event_detail`   | 单个事件的错误、栈、以及相对报错时间的操作与请求时间线      |
| `get_source_context` | 通过 Source Map 的 `sourcesContent` 读取出错行前后 5 行源码 |
| `compare_releases`   | 各版本的事件数、占比、首次出现时间、是否有 Source Map       |

报告通过第 6 个工具 `submit_report` 提交。每个工具结果正文第一行写着编号（`ref: T3`），每条证据必须带
这个编号和从该次结果里逐字摘出的 `quote`，服务端确定性核对：调用存在、调用成功、原文确实出现在结果里。

最初的设计是引用 `tool_call_id`。它只存在于 chat/completions 的消息元数据里，模型读不到；第一次接真实
模型（DeepSeek）时引用有效率为 0，模型先引用工具名、再编造 id。本地测试没能发现，因为测试替身知道自己
发出的 id。不通过时，问题清单作为
工具结果退回模型修正。报告最多提交 3 次（首次加 2 次重交）：第 3 次仍有未核实的引用时，只要报告的形状
合法就接受，并如实标出未核实的引用；形状都不合法则调查以失败结束。

### 边界

- **只读**：没有任何写数据、改代码、执行命令或访问外部网络的工具。模型即使被注入，也造不成写操作。
- **作用域绑定**：工具只能看到本次调查的 Issue 及其项目，参数里的 `eventId` 也校验归属。
- **不可信输入**：错误消息、URL、按钮文字、栈都可能被终端用户控制，是间接提示词注入的入口。
  提示词把工具结果声明为数据，评测集里有专门的注入用例。
- **硬上限**：收集证据最多 8 轮、每轮最多 4 个工具调用、累计输入 8 万 token、单工具 5 秒、
  整次运行 180 秒、全局同时 3 个运行、同一 Issue 同时 1 个。预算用尽后只保留 `submit_report`
  并强制调用。
- **源码外发**：`get_source_context` 会把出错行附近的源码发给模型服务商，可用
  `AGENT_SOURCE_CONTEXT=false` 关闭，关闭后工具如实返回不可用。

### 过程可见

每个事件（开始一步、文本增量、工具调用与结果、报告被驳回、结束）带运行内单调递增的 `seq`
写入 `investigation_events`，再推给订阅者。前端用 SSE 订阅：

- 断线后浏览器带 `Last-Event-ID` 重连，服务端从库里回放缺失部分；
- 服务端先订阅、再回放，按 `seq` 去重，不漏不重；
- 运行与连接解耦，关掉页面不等于取消，只有显式取消请求才会中止；
- 运行结束且没有新事件时返回 204，让 EventSource 停止重连。

## 替代方案

- **继续单次调用，只加引用校验**：成本低，但解决不了「看不到快照之外的证据」。评测里保留它作为对照组。
- **LangChain / LangGraph**：循环本身只有一百多行，而每个上限和失败分支都需要能解释清楚；
  引入框架换来的是更少的代码，但也把这些决定藏进了框架。状态图、checkpoint、interrupt
  这些概念在本项目里分别对应：循环里的 `messages` 数组、事件日志、取消请求。
- **Responses API**：单次诊断沿用它。Agent 改用 chat/completions 的工具调用，因为 DeepSeek、
  通义千问、豆包等 OpenAI 兼容端点对它的支持最一致。
- **WebSocket 推送**：数据只从服务端流向浏览器，取消走普通 POST 即可；SSE 基于普通 HTTP，
  自带重连和续传语义，代价是 EventSource 只能 GET、不能自定义请求头，需要鉴权时要换成
  fetch + ReadableStream 自己解析。

## 影响

- 调查比单次调用慢、贵：多轮调用，每轮都重发整段对话。评测报告记录了两者的 token 与耗时。
- 没有密钥时由确定性脚本驱动同一个循环、同一批工具和校验，用于离线演示与 E2E，界面明确标注它不是模型推理。
- 引用校验能抓住编造的调用、编造或改写的原文，抓不住「原文属实但推理错误」。后者只能靠评测集和人工判断。
