# ADR 0011：告警顺带发起排障调查，结论跟进到同一个渠道

- 状态：已采纳，建立在 ADR 0003（只读排障 Agent）与 ADR 0010（生命周期与告警）之上
- 日期：2026-10-02

## 背景

告警只说「出事了」。工程师收到后要打开工作台、找到 Issue、点开始调查、等它跑完——这几分钟正是事故里最贵的时间。
行业里的做法是让 AI 在告警时就开始查：Datadog 的 Bits AI SRE 在监控告警时自动调查并把结论发回 Slack；Sentry 的 Seer 可以
对新问题自动跑根因分析，并按「可修复程度」和频率控制成本。

自动调查的风险也很清楚：每次调查都是多次计费的模型调用；一次发版带来几十个新 Issue 时，不加限制就是几十次调查；
同一个问题来回回归，就会被反复调查。

## 决策

1. **按规则开启**：告警规则多一个动作「顺带发起调查」（`autoInvestigate`），和通知共用触发条件、级别和静默。
   只有真正发出的告警才发起调查：被静默、去重、超出上限的告警没人会收到，也就没人等这份报告。
2. **两道闸**：每个项目 24 小时（滚动窗口）内告警最多发起 `AUTO_INVESTIGATIONS_PER_DAY` 次（默认 10，0 关闭）；
   同一个 Issue 24 小时内已经调查过（不论人点的还是告警发起的）就不再自动发起。同时进行的调查已满时不排队，记为 busy。
   没有发起的原因记在通知上（cooldown / daily_limit / busy / disabled）。
3. **结论跟进**：调查结束后，给发起它的那条规则的渠道排一条跟进通知（走同一个发件箱）：摘要、首要原因及置信度、
   引用核验了几条；失败时说明停在哪里。离线脚本跑的如实标注「不是模型推理」。
4. **来源可见**：`investigation_runs.started_by` 记 person / alert，工作台的调查面板注明「由告警规则自动发起」，
   每日上限只数告警发起的。

## 替代方案

- **每个新 Issue 都自动调查（不挂在告警规则上）**：成本不可控，也和「谁关心这个问题」脱节；挂在规则上，
  调查的范围就是团队已经声明关心的那些。
- **排队等空位**：同时进行的调查已满时排队，会在事故高峰积压一串过时的调查；直接跳过并记下原因更可预期，
  工程师可以手动发起。
- **只在工作台里显示结论、不发跟进通知**：工程师还是要先打开工作台；跟进通知把结论送到他已经在看的地方。
- **按 Sentry 的「可修复程度」评分决定要不要调查**：需要先有一个打分模型；每日上限 + 冷却是更简单、可解释的成本控制，
  以后可以在它前面加打分。

## 影响

- 迁移 8：规则多一列 `auto_investigate`，通知多 `investigation_id`、`investigation_note`，调查多 `started_by`。
- 调查的输入是不可信的遥测，跟进通知里的结论同样经过渠道的转义（ADR 0010）。
- 上限按项目计，多个项目时总量是「项目数 × 上限」；多实例部署时上限要放到共享存储里计数。
