# ADR 0004：先还原再聚合，指纹与 Issue 多对一

- 状态：已采纳
- 日期：2026-10-01

## 背景

聚合决定「哪些错误算同一个 Issue」。原来的指纹在入库时计算，用的是**压缩后**的栈顶帧，Source Map 还原在入库之后才做：

```text
at t (https://shop.example/assets/checkout.a81e93bd.js:1:420)
```

压缩器给函数起的短名（`t`、`n`）和列号取决于整个文件的内容，任何一处改动、重新构建之后都可能变化。于是：

1. 同一个 bug 每发一次版就成了一个新 Issue，事件数、影响用户和趋势被拆散在几个 Issue 里；
2. 「已解决的 Issue 再次发生就重新打开」失效：新版本里再次发生的同一个 bug 是一个全新的 Issue，而不是回归；
3. 栈顶是依赖包的帧时（崩在 React 内部），所有在渲染时出错的问题共享同一个栈顶帧，按消息才区分得开。

指纹又直接存在 `issues` 表的唯一键上，一个 Issue 只能有一个指纹：改算法就意味着所有正在发生的问题都换一个新 Issue，
人工合并也无从做起。

## 决策

1. **接入分三段：规范化 → 还原 → 聚合入库**。还原在聚合之前、事务之外进行（读 map 是异步的，SQLite 事务必须同步执行完）。
2. **指纹 v2 按源码位置**：`SHA-256(v2 | 类型 | 消息 | 聚合帧 [| 业务码])`。聚合帧取第一个应用自己的帧，跳过
   `node_modules`、浏览器扩展和打包器运行时的帧；映射到源码时用「源文件 + 函数名 + 出错那行代码」，不看行列号——
   前面加几行代码不应该让同一个 bug 变成新 Issue。映射不到时用压缩后的这一帧，与 v1 相同。
3. **指纹与 Issue 多对一**：新表 `issue_fingerprints(project_id, fingerprint) → issue_id`（迁移 3），已有 Issue 的指纹
   原样搬进来并标为 v1。v2 指纹找不到 Issue 时，按 v1 再算一次去找，找到就把 v2 指纹登记到原来的 Issue 上：
   算法升级不会打断正在发生的问题。
4. **合并**：`POST /api/v1/issues/:issueId/merge` 把被合并方的指纹、事件和调查记录改指向目标，重新统计计数后删除
   被合并方。指纹一起迁移，之后的同类事件直接归入目标。工作台的 Issue 列表可以勾选合并。
5. **自定义指纹**：事件可带 `fingerprint`，`'{{ default }}'` 代表默认指纹，用来在默认结果上细分或跨位置合并。

这与 Sentry 的做法一致：先处理（还原）再计算分组哈希、只看应用自己的帧、一个分组可以有多个哈希、升级分组配置时
同时计算新旧两个哈希、支持合并和 `fingerprint`。

## 替代方案

- **继续按压缩帧聚合，只把列号归一化掉**：短名本身也会变，`at t` 和 `at n` 仍是两个指纹；还会把同一文件里不同位置的
  错误并到一起。
- **map 上传后重新聚合已有事件**：要拆分、合并已有 Issue，事件计数、处理状态、调查记录都要跟着迁移，代价和出错面都大；
  Sentry 也不这样做，而是要求 map 在流量之前上传。
- **用 Embedding 找相似 Issue 自动合并**（Sentry 2024 年上线，新 Issue 减少 40%）：需要模型服务，作为可选的后续增强；
  人工合并是它的兜底，也是它的前提（要有「多个指纹指向一个 Issue」的数据模型）。
- **对整段堆栈求指纹**：调用路径不同（从哪个页面、哪个按钮进来）就会拆开同一个 bug。

## 影响

- **聚合依赖 map 先到**：某个版本没有 map 时，它的事件按压缩帧聚合，与有 map 的版本里的同一个 bug 分成两个 Issue；
  事后补传 map 只回填 `original_stack`，不重新聚合。所以 map 应在构建时上传，分开了的 Issue 手动合并。
  演示数据因此为两个版本都上传了 map。
- 接入的事务之前多了一段异步还原；同机基准持平（10 事件批次 P50 3.89 → 3.05 ms，带堆栈的批次 3.75 → 3.72 ms，
  差异在波动范围内），解析结果本来就跨请求缓存。
- 拿不到响应的请求（状态码 0）的级别从 warning 改为 error，与 SDK 默认的失败判定一致。
- 合并不可撤销，暂不支持拆分。
