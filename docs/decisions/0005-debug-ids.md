# ADR 0005：用 Debug ID 关联产物与 Source Map，构建插件负责注入和上传

- 状态：已采纳
- 日期：2026-10-01

## 背景

服务端原来按「事件的 Release + 栈帧文件名」找 Source Map，这依赖两个由人保证的前提：

1. **SDK 的 `release` 与上传 map 时填的版本号一致**。两处配置分别在运行时和 CI 里，配错一次，这个版本的所有错误都还原
   不了。ADR 0004 之后影响更大：聚合在还原之后，还原不了的错误按压缩位置聚合，同一个 bug 和有 map 的版本分成两个 Issue。
2. **同一个版本里同一个文件名只对应一份内容**。文件名不带内容哈希、同一个版本号重新构建过（例如热修复没改版本号）时，
   新上传的 map 覆盖旧的，发版过程中旧页面上报的错误被新 map 还原出一个看似合理却错误的位置。错误的还原比没有还原更糟：
   开发者和排障 Agent 都会去看一行不相干的代码。

上传本身也是手动的一步（演练场原来用一个单独的脚本扫描 `dist`、上传、删除），容易漏，漏了就落到第 1 条的后果。

Sentry 把「release / dist / URL 对不上」列为 Source Map 最常见的问题，2023 年起改用 Debug ID；ECMA-426（Source Map
规范）也有对应的 Debug ID 提案。

## 决策

1. **构建插件**（`packages/vite-plugin`）在 `generateBundle` 里对每个 JS 产物：由压缩后的内容算出 Debug ID（SHA-256 →
   UUID），产物开头插一行登记代码、末尾加 `//# debugId=`，map 的 `mappings` 前加一个分号并写入 `debugId`，然后把 map 从
   bundle 里删掉；产物写盘之后上传 map。上传失败默认让构建失败。
2. **登记代码**在文件顶层 `new Error()`，以它的 stack 为键、Debug ID 为值写进全局登记表；**SDK** 出错时把登记表解析成
   「文件地址 → Debug ID」，事件带上堆栈里出现的文件的 `debugIds`。
3. **服务端**逐帧先按 Debug ID 在事件所属的项目里找 map，不看事件声明的版本；找不到再按版本 + 文件名。事件的 `debugIds`
   存进 `context_json`，事后上传的 map 按它回填，排障 Agent 读源码时也用它。
4. **唯一键**改为「版本 + 文件名 + Debug ID」（迁移 4）：同名不同内容的两份 map 并存。Debug ID 不设全局唯一。

## 替代方案

- **只校验、不改模型**：上传时检查版本号是否已有事件。能发现「版本号还没人用」，发现不了「版本号用错了」，也解决不了
  同名不同内容。
- **按 URL 的完整路径而不是文件名找 map**：解决同名文件分属不同目录，解决不了上面两条。
- **用 `import.meta.url` 登记**：代码更短、SDK 不必解析堆栈，但只有 ES 模块有；CJS、IIFE 产物（库模式、旧浏览器的
  legacy 构建）拿不到。`document.currentScript` 在 ES 模块里是 null。
- **在 `renderChunk` 里注入**：打包器会帮忙合并 map，但这时代码还会被压缩改写，Debug ID 对应的不是最终部署的内容。
- **把 map 和产物一起部署、靠 `sourceMappingURL` 让服务端去取**：map 常常内联全部源码，部署出去就是公开源码。
- **Debug ID 全局唯一**：没改动的 vendor 文件在相邻两个版本里内容相同、Debug ID 相同，第二次上传会被拒绝。

## 影响

- 版本号配错、同名文件重新构建，都不再导致还原失败或还原错误；旧版 SDK 和手动上传的 map 照旧按版本 + 文件名工作。
- 按 Debug ID 查找必须限定在项目内：它写在公开的产物文件里，不是秘密。
- 每个 JS 产物多一行登记代码（239 字节）；SDK 多一个模块（解析登记表），体积见性能报告；页面加载时只多一次
  `new Error()`，解析留到出错时。
- 文件名里的内容哈希是注入之前算的；注入内容由注入前的代码决定，哈希仍随内容变化。
- 按 Debug ID 回填没有单独的索引，代价随项目事件数线性增长，只在上传时发生。
- 目前只有 Vite 插件；上传接口仍无鉴权。
